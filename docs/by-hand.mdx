These are the commands that your agent runs for you in the [Quickstart](/quickstart). Install piloop first, and log
in to at least one coding agent CLI: `claude auth login`, `codex login`, or `/login` in `pi`.

## The enwik8 example

The **enwik8** example is a small [Hutter Prize](http://prize.hutter1.net/): compress the first 10 MB of Wikipedia
into as few bytes as possible. The agents edit `compressor.py`. The baseline is zlib.

<Steps>
  <Step title="Create the campaign">
    ```bash
    piloop init --example enwik8 ~/piloop-enwik8
    cd ~/piloop-enwik8
    ```

    `piloop init` copies the example, downloads the data, makes a git repo, starts the daemon and measures the
    baseline. The daemon's log is `~/.piloop/serve.log`.

    ```text
    daemon started: pid 41213, log ~/.piloop/serve.log
    campaign enwik8 #1 registered; measuring baseline candidate#1 (`piloop eval queue` shows it; Ctrl-C stops only the wait)
    baseline candidate#1: bytes 3688775, seconds 0.67
    ```

    The example uses Claude Code. To use Codex or pi too, edit `harnesses` in `piloop.toml`, for example
    `harnesses = ["claude", "codex"]`, and run `piloop init` again.
  </Step>
  <Step title="Add an idea">
    ```bash
    piloop idea add enwik8 "Try lzma at the highest preset"
    ```

    ```text
    idea#1 ready p2: Try lzma at the highest preset
    ```

    The daemon starts an implementer for the idea. When the backlog is short, the research agent adds more ideas.
  </Step>
  <Step title="Watch the campaign">
    ```bash
    piloop watch
    ```

    Press `enter` to open the campaign, and `q` to quit. The daemon continues to run.
  </Step>
</Steps>

## What happens

The implementer edits `compressor.py` and commits. The daemon runs `evaluate.py` on the commit. The script checks that
the round trip gives back the exact input, then prints two metrics:

```toml
[[metrics]]
name = "bytes"       # the compressed size plus the size of compressor.py
direction = "lower"
role = "primary"     # the metric to improve

[[metrics]]
name = "seconds"     # the CPU time to compress and decompress
direction = "lower"
role = "guardrail"   # may get worse
margin = 60          # by at most 60 s from the head
floor = 120          # and never past 120 s
repeats = 3          # a time: measured 3 times next to the head
```

A commit with fewer bytes that holds the guardrail is a `keep`, and the next runs start from it. In this run, the
lzma idea took 2 minutes and 356k tokens:

```bash
piloop status enwik8
```

```text
enwik8 · head bytes 2720458 (candidate#2, -968317 vs baseline) · 2 kept / 2 candidates · 356k tok · evaluator #1, 3m old
```

The verdict says why:

```text
against candidate#1: bytes 2720458 vs 3688775 (-968317; 95% worst case -968317 over 3 pairs); guardrails: seconds 10.9 vs 0.8467 (+10.05; 95% worst case +10.28 over 3 pairs) within its margin 60
```

The example stops after 20 scored runs (`[plugins.stop_rule] max_runs`). See [the verdict](/concepts/verdict) for the rules.

To let an agent answer the escalations, open your coding agent in `~/piloop-enwik8` and ask it to "orchestrate the
piloop campaign". See [The orchestrator and the inbox](/concepts/orchestrator).

The second example, `piloop init --example titanic-tracks ~/piloop-titanic`, has two objectives. See
[Tracks](/concepts/tracks). The third, `inference`, makes a small model serve faster: see
[Optimize inference](/guides/inference-optimization).

## Your own repo

<Steps>
  <Step title="Create the files">
    ```bash
    cd my-repo
    piloop init
    ```

    `piloop init` writes `piloop.toml`, `brief.md` and a stub `evaluate.py`, and commits them. It keeps every file
    that exists already. It stops while `evaluate.py` is the stub.

    <Warning>
      If your repo has an `evaluate.py` already, `piloop init` keeps it and does not stop. It registers the campaign
      with the template's `piloop.toml`, whose baseline usually fails to evaluate, and that pauses the campaign until you fix it.
    </Warning>
  </Step>
  <Step title="Write the evaluate command">
    Make `evaluate.py` measure your code, or set `evaluate` in `piloop.toml` to a command that you have. It writes one
    JSON line with each metric to `$PILOOP_RESULT_FILE`. See [the evaluate command](/concepts/campaigns#the-evaluate-command).
  </Step>
  <Step title="Edit piloop.toml">
    Set `name`, `evaluate`, the `[[metrics]]` tables, `harnesses` and the `model` of each harness. The template lists every key, and the
    [configuration reference](/reference/configuration) describes them. The daemon enforces only the limits in
    `piloop.toml`, not the ones in `brief.md`.
  </Step>
  <Step title="Edit brief.md">
    Tell the implementers what to improve, which files they may edit, which files they must not touch, and what needs
    a human decision. Keep it under 400 words: `piloop init` and `piloop doctor` warn past `[agents] brief_words`. When
    the campaign changes, rewrite the brief to that size: never append a rule.
  </Step>
  <Step title="Register the campaign">
    ```bash
    piloop init
    ```

    This commits your edits, starts the daemon and measures `HEAD` as the baseline. A baseline that surprises you usually means that the
    evaluate command is wrong.
  </Step>
  <Step title="Start the campaign">
    ```bash
    piloop idea add my-repo "Cache the parsed input" --hypothesis "Parsing takes 40% of the time" --priority 1
    piloop watch
    ```

    The campaign name is the `name` in `piloop.toml`, by default the name of the directory.
  </Step>
</Steps>

## Change the configuration

Edit `piloop.toml` and run `piloop init` again. The daemon uses the copy that the last `piloop init` stored, so an
edit has no effect before that. A change to the evaluate command, or to the name or direction of a metric, makes a new
[evaluator](/concepts/campaigns#evaluators), and the daemon measures the head again.
