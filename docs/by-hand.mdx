These are the commands that your agent runs for you in the [Quickstart](/quickstart). Install piloop first, and log
in to Claude Code (`claude auth login`) or Codex (`codex login`).

## The enwik8 example

The **enwik8** example is a small [Hutter Prize](http://prize.hutter1.net/): compress the first 10 MB of Wikipedia
into as few bytes as possible. The agents edit `compressor.py`. The baseline is zlib.

<Steps>
  <Step title="Create the campaign">
    ```bash
    piloop init --example enwik8 ~/piloop-enwik8
    cd ~/piloop-enwik8
    ```

    `piloop init` copies the example, downloads the data, makes a git repo, starts the daemon and measures the
    baseline:

    ```text
    daemon started: pid 41213, log ~/.piloop/serve.log
    campaign enwik8 #1 registered; measuring baseline candidate#1 (`piloop eval queue` shows it; Ctrl-C stops only the wait)
    baseline candidate#1: bytes 3688775, seconds 0.67
    ```

    The example uses Claude Code. To add Codex, add `"codex"` to `use` in `[plugins.harness]` of `piloop.toml`, give
    it a `[plugins.harness.codex]` table with its `model`, and run `piloop init` again.
  </Step>
  <Step title="Add an idea">
    ```bash
    piloop idea add enwik8 "Try lzma at the highest preset"
    ```

    ```text
    idea#1 open p2: Try lzma at the highest preset
    ```

    The daemon starts a run on each free implementer slot. Each implementer claims an open idea, or proposes its own.
  </Step>
  <Step title="Watch the campaign">
    ```bash
    piloop watch
    ```

    Press `enter` to open the campaign, and `q` to quit. The daemon goes on.
  </Step>
</Steps>

## What happens

The implementer edits `compressor.py`, commits and submits. The daemon runs `evaluate.py` on the commit. The script
checks that the round trip gives back the exact input, then reports two metrics:

```toml
[[metrics]]
name = "bytes"       # the compressed size plus the size of compressor.py
direction = "lower"
role = "primary"     # the metric to improve

[[metrics]]
name = "seconds"     # the CPU time to compress and decompress
direction = "lower"
role = "guardrail"   # may get worse
margin = 60          # by at most 60 s from the baseline
floor = 120          # and never past 120 s
```

The daemon scores each submission into the campaign's [pool](/concepts/pool). A candidate with fewer bytes than the
best, that holds the guardrail, becomes the best, and the next runs start from it. Here the lzma idea took 2 minutes
and 356k tokens:

```bash
piloop status enwik8
```

```text
## Campaign

best: candidate#2 · bytes: 2720458 · bytes vs baseline: +968317 · may be best on bytes: 2 · candidates: 2 · tokens: 356214 · evaluator: #1, 3m old
```

The implementer heard where its commit stands:

```text
[piloop] candidate#2 (3f2c9a1b7d04): bytes 2720458 over 1 eval: the best of the bytes track now, rank 1 of 2; vs parent +968317
```

The example stops after 20 scored runs (`[plugins.stop_rule] max_runs`). To let an agent answer the escalations, open
your coding agent in `~/piloop-enwik8` and ask it to "orchestrate the piloop campaign".

Two more examples: `titanic-tracks` has two objectives ([Tracks](/concepts/pool#tracks)), and `inference` makes a small
model serve faster ([Optimize inference](/guides/inference-optimization)).

## Your own repo

<Steps>
  <Step title="Create the files">
    ```bash
    cd my-repo
    piloop init
    ```

    `piloop init` writes `piloop.toml`, `brief.md` and a stub `evaluate.py`, and commits them. It keeps every file
    that exists already, and stops while `evaluate.py` is the stub. With an `evaluate.py` of your own, it does not
    stop: it registers the campaign with the template's `piloop.toml`, whose baseline usually fails and pauses the
    campaign. Then fix `piloop.toml` and run `piloop init` again.
  </Step>
  <Step title="Write the evaluate command">
    Make `evaluate.py` measure your code, or set `evaluate` in `piloop.toml` to a command that you have. See
    [the evaluate command](/concepts/campaigns#the-evaluate-command).
  </Step>
  <Step title="Edit piloop.toml">
    Set `name`, `evaluate`, the `[[metrics]]` tables, `use` in `[plugins.harness]`, and the `model` of each harness.
    Set the budget in `[plugins.stop_rule]`: `max_hours`, and a USD cap ([Stop conditions and cost](/concepts/cost)).
    The template lists every key, and the [configuration reference](/reference/configuration) describes them.
  </Step>
  <Step title="Edit brief.md">
    Tell the implementers what to improve, which files they may edit, which they must not touch, and what needs a
    human decision. Keep it under 400 words (`[agents] brief_words`). When the campaign changes, rewrite the brief:
    never append a rule.
  </Step>
  <Step title="Register the campaign">
    ```bash
    piloop init
    ```

    This commits your edits, starts the daemon and measures `HEAD` as the baseline. Runs start at once, and the
    implementers propose their own ideas. To give them yours:

    ```bash
    piloop idea add my-repo "Cache the parsed input" --hypothesis "Parsing takes 40% of the time" --priority 1
    ```

    The campaign's name is `name` in `piloop.toml`, by default the name of the directory.
  </Step>
</Steps>

## Change the configuration

Edit `piloop.toml` and run `piloop init` again: the daemon uses the copy that the last `piloop init` stored. A change
to the evaluate command, or to the name or direction of a metric, makes a new
[evaluator](/concepts/campaigns#evaluators).
