A **worker** runs the daemon's jobs: agent sessions and evaluations. `piloop serve` has one, called `serve`, and
`piloop worker` adds one on another machine. A job's code, inputs and results go through the
[CAS](/concepts/memory#the-cas), so the worker and the server share one.

## Capacity

A **pool** is the capacity of each worker in it: its slots, and the thresholds that keep jobs off a busy host.
`piloop serve`'s worker is in the pool `serve`:

```toml
[plugins.executor]
provider = "workers"

[plugins.executor.pools.serve]
agents = 2
slots = { evaluation = 1 }
max_load = 1.5      # the 1-minute load per CPU
min_memory_gb = 4
```

A worker over `max_load` or under `min_memory_gb` takes no job. The daemon launches an agent only into a free slot,
and gives it to the campaign that the [launch policy](/plugins/rules#launch-policies) picks: by default, the one with
the fewest live agents. To change a pool's key while the daemon runs, set a **limit**. It wins over `config.toml`, and
`piloop status` shows it with its reason:

```bash
piloop limits set executor.pools.serve.slots.evaluation=1 --reason "the GPU trains a model"
piloop limits unset executor.pools.serve.slots.evaluation
```

```text
executor.pools.serve.slots.evaluation = 1: the daemon applies it at once
executor.pools.serve.slots.evaluation: the limit is gone
```

`piloop worker list` shows each worker, and why it got no lease:

```text
 worker  pool   seen    load     memory   disk      agents  evaluation  no lease
 serve   serve  6s ago  78.1/32  60.8 GB  379.3 GB  0       0           slots
```

A worker that misses its heartbeats for `grace_seconds` counts zero slots. After `toleration_seconds`, its leases
expire and their jobs go back to the queue. A worker that hears nothing back stops its own jobs before its leases
expire, so a job never runs twice. Both are keys of [`[plugins.executor]`](/reference/configuration#plugins).

## Add a worker on another machine

On the server, give the worker's pool its slots in `config.toml`:

```toml
[plugins.executor.pools.gpu]
agents = 2
slots = { evaluation = 1 }
```

Set `tls` in `[plugins.network]` (see [On a server](/guides/daemon#on-a-server)). Then listen, serve the CAS, and make
the worker's token. `piloop init` started a daemon on the socket only, so stop it first:

```bash
piloop stop
piloop serve --detach --listen 0.0.0.0:8443
piloop cas serve --listen 0.0.0.0:7701
piloop token create gpu1
```

When the server's `[plugins.cas]` is a bucket that the worker can reach, skip `piloop cas serve`, and give the worker
the same `[plugins.cas]`.

On the worker, install the same piloop as on the server, and log in to the harnesses that its agents use. In its
`config.toml`:

```toml
[plugins.cas]
provider = "cached"
local_max_gb = 50
remote = { provider = "http", url = "https://piloop.example.com:7701" }
```

```bash
PILOOP_HTTPS_TOKEN=<token> piloop worker --server https://piloop.example.com:8443 --pool gpu
```

The worker's name is the token's name. It calls the server, and the server never calls it. On the server,
`piloop worker list` shows it:

```text
 worker  pool   seen    load     memory    disk      agents  evaluation  no lease
 gpu1    gpu    6s ago  21.8/32  103.8 GB  816.4 GB  1       0           nothing
 serve   serve  6s ago  21.8/32  103.8 GB  816.4 GB  0       0           slots
```

The server refuses a worker with another piloop protocol, an unknown pool, a revoked token, or a `[plugins.cas]` that
is not the server's. The worker then stops its jobs and exits with the reason.

## Workers that the server starts

A pool with a **provisioner** starts its own workers when jobs wait, and stops them when they idle. Each waiting job
that no free slot takes starts a worker, up to `max`. A worker that held no job for `idle_seconds` is drained and
stopped. A worker that cannot reach its server for `orphan_exit_seconds` exits by itself.

On Modal, each worker is a sandbox of an image with `piloop` in it:

```toml
[plugins.network]
listen = "0.0.0.0:8443"
tls = "proxy"
url = "https://piloop.example.com:8443"

[plugins.executor.pools.gpu]
agents = 0
slots = { evaluation = 1 }
runners = ["process"]

[plugins.executor.pools.gpu.provisioner]
max = 4

[plugins.executor.pools.gpu.provisioner.compute]
provider = "modal"
image = "ghcr.io/acme/piloop-worker:0.3"
gpu = "A100"
secrets = ["piloop-cas"]
```

- Each worker gets a token of its own, and dials `url`. Give it the server's `[plugins.cas]` in its image, or as
  `PILOOP_PLUGINS` in the provider's `env`.
- `secrets` names the Modal Secrets that each sandbox gets as its environment, for the worker itself, such as a
  bucket's credentials. A job's keys are piloop [secrets](/guides/secrets), which the worker gets when the job starts.
- `registry = { kind = "aws-ecr", secret = "<modal secret>" }` pulls from a private registry. `basic` takes
  `REGISTRY_USERNAME` and `REGISTRY_PASSWORD`.
- The server needs Modal's credentials and `piloop[modal]`.

On Daytona, each worker is a sandbox of a snapshot with `piloop` in it:

```toml
[plugins.executor.pools.eval]
agents = 0
slots = { evaluation = 1 }
runners = ["process"]

[plugins.executor.pools.eval.provisioner]
max = 4

[plugins.executor.pools.eval.provisioner.compute]
provider = "daytona"
snapshot = "piloop-worker-0.5"
ttl_hours = 4
```

- In place of `snapshot`, an `image` is built into a snapshot at its first sandbox, sized with `cpu`, `memory_gib`
  and `disk_gib`.
- Daytona's API shows a sandbox's `env`, so put no secret there. `secrets` maps a variable to a Daytona Secret.
- Daytona deletes a sandbox after `ttl_hours`, 24 by default.
- The server needs `DAYTONA_API_KEY` and `piloop[daytona]`.

The [configuration reference](/reference/configuration#plugins) lists each provider's keys. To stop every worker of a
pool, drain them:

```bash
piloop limits set executor.pools.gpu.provisioner.max=0 --reason "the GPU budget is spent"
```

## Behind an authenticating proxy

When a proxy in front of the server authenticates every caller (see
[Behind an authenticating proxy](/guides/daemon#behind-an-authenticating-proxy)), give the workers a rule of their
own:

```toml
[plugins.network]
provider = "proxy"
listen = "0.0.0.0:8443"
url = "https://piloop.example.com"
claims = { org = "x-org-id", kind = "x-subject-kind", user = "x-user-id", principal = "x-principal" }
name_claims = ["user", "principal"]
rules = [
  { when = { org = "acme", principal = "key-0123" }, access = "worker" },
  { when = { org = "acme", kind = "service_account" }, access = "act", caller = "service" },
  { when = { org = "acme" }, access = "act" },
]
```

The first rule that matches wins, and no match is refused. A worker names itself in `x-piloop-worker`, and anyone
else by the first of its `name_claims` that is not empty. The proxy must remove any copy of these headers that a
caller sends.

Workers share one credential that the proxy accepts and the `worker` rule matches. Store it as a secret, which each
provisioned worker gets:

```bash
printf %s "$WORKER_KEY" | piloop secret set PILOOP_WORKER_CREDENTIAL
```

Give a provisioned worker the same network with `PILOOP_PLUGINS='{"network": {"provider": "proxy"}}'` in the
provider's `env`.

## What an agent on a worker gets

- The worker's environment, and the [secrets](/guides/secrets) that its job names.
- A clone of the campaign's repo and a copy of the shared workspace. Its commits and workspace writes come back when
  it ends.
- Its `piloop` commands, which the worker relays to the server while the agent's job runs.

Its session goes to the server's CAS at least every 30 seconds, so `piloop attach` shows what it wrote, and a lost
worker loses at most those 30 seconds.

<Warning>
  An agent on a worker runs as the worker's user, so it holds the worker's token. It can do whatever the worker can
  do on the server. Run a worker as a user that you give that trust.
</Warning>

## Faults

| What happens | What piloop does |
|---|---|
| A worker dies during a run | The run ends `worker_lost`. It is not an attempt. |
| A worker dies during an evaluation | The evaluation is queued again. Partial output is never scored. |
| A worker stops before it sends a report | The report waits in `$PILOOP_HOME/spool/<worker>`, and goes out when the worker starts again. |
| The server does not answer | The worker tries each call again. Its log says `worker.unreachable`. |
| `piloop serve` restarts | Its worker finds its leases again and re-attaches to each agent. |
| A started worker does not register within `register_seconds` | It is stopped, and the pool backs off before it starts another. |
| The platform refuses a start: a quota, no GPU | The pool backs off. Three refusals in a row are an escalation in the inbox. |
