```bash
piloop upgrade
```

The command prints each step as it runs it:

1. It upgrades the CLI from the source that you installed it from: PyPI (the latest release), the GitHub repo (the
   latest `main`), or a local checkout. It prints the version before and after.
2. It runs `piloop install-skills` from the new code, so the skills of every harness on your `PATH` match the new CLI.
3. It restarts a running daemon in place, as `piloop restart` does. The running agents continue, and the new code
   migrates the database as it starts. First it checks that the new daemon starts (`piloop serve --check`): when it
   would not, the upgrade stops with the reason and the old daemon keeps running. When no daemon runs, the upgrade
   migrates the database itself.
4. It runs `piloop doctor`. When a check fails, the upgrade exits with a non-zero status.

`piloop --version` prints the version, and the commit for an install from the GitHub repo. A checkout that you
installed with `uv sync` is not a uv tool: upgrade it with `git pull`.

## Upgrade one release at a time

Upgrade through every minor release in order: 0.4 to 0.5, then 0.5 to 0.6, then 0.6 to 0.7, then 0.7 to 0.8. Each release migrates a database only from
the newest schema of the minor release before it, or from a newer one. On an older database, every command names the
release that it is from, and the release to install first. It changes nothing:

```bash
uv tool install 'piloop==0.7.*'
piloop upgrade
```

Then install the next release in the same way. `uv tool install piloop` drops the pin. Quote the requirement: `*` is
a glob in zsh.

This page covers the upgrades to the next release, 0.8.0, 0.7.0 and 0.6.0. For an earlier one, follow the guide of the release that you upgrade to:
[0.5.0](https://github.com/hiloopai/piloop/blob/v0.5.0/docs/guides/upgrading.mdx),
[0.4.0](https://github.com/hiloopai/piloop/blob/v0.4.0/docs/guides/upgrading.mdx),
[0.3.1](https://github.com/hiloopai/piloop/blob/v0.3.1/docs/guides/upgrading.mdx) or
[0.2.1](https://github.com/hiloopai/piloop/blob/v0.2.1/docs/guides/upgrading.mdx).

## Who upgrades during a campaign

The runs after an upgrade are scored by the new code. So the orchestrator does not upgrade by itself: when
`piloop doctor` reports a newer piloop, it asks you in the inbox. Set `PILOOP_AUTO_UPGRADE=1` in its environment to let
it upgrade and record the decision instead.

## Check the install

`piloop doctor` is read-only. It checks:

- Whether the source that you installed from has a newer piloop. An install pinned to a version is not checked.
- The daemon runs the installed code, and the database has the current schema.
- The providers that packages add load, and none of them reuses a name.
- The `piloop.toml` of every campaign loads, and the secrets that its MCP servers and harnesses need are set.
- Every harness on your `PATH` has the skills of this CLI.
- What each provider in use checks itself, such as the harness CLIs on your `PATH` and git 2.40 or later.

Each failure says how to fix it. Set `PILOOP_DEBUG=1` to see the full traceback of an unexpected error.

## The database

`piloop migrate`, `piloop upgrade`, and `piloop serve` when the daemon starts, migrate the database to the schema of
their piloop. Every other command opens the database only at the schema that it knows. Otherwise it changes nothing,
and says what to run:

- The database is older, and no daemon runs: run `piloop migrate`.
- The database is older, and a daemon runs: run `piloop restart`, which migrates it on this piloop.
- A newer piloop, or one built from another branch, migrated it: install that piloop.

While a daemon of an older piloop runs, `piloop migrate` and `piloop serve` do not migrate, because that daemon would
break on the new schema.

Before it migrates, piloop writes a copy of the database next to it:
`$PILOOP_HOME/piloop.db.bak-<revision>-<UTC time>`, such as `piloop.db.bak-0001-20261021T002254Z`. It keeps the 3
newest copies: `migration_backups` in `config.toml` sets how many, and `0` writes none. When the copy cannot be written,
nothing is migrated.

### Restore from the backup

A backup brings the database back to the moment before the migration. What piloop wrote after it is lost. The git
commits and the workspace files stay.

1. Stop the daemon: `piloop stop`.
2. Install the piloop that the backup's revision belongs to. A newer one would migrate the copy again.
3. Put the copy in place of the database, and remove its `-wal` and `-shm` files:

   ```bash
   cd "${PILOOP_HOME:-$HOME/.piloop}"
   mv piloop.db piloop.db.failed && rm -f piloop.db-wal piloop.db-shm
   cp piloop.db.bak-0001-20261021T002254Z piloop.db
   ```

4. Start the daemon, `piloop serve --detach`, and check with `piloop doctor`.

## Follow main

To follow `main` instead of the releases, install piloop from the repo. From then on, `piloop upgrade` installs the
latest `main`, and a release opens the database again only once it knows the schema that `main` gave it.

```bash
uv tool install --reinstall 'git+https://github.com/hiloopai/piloop'
piloop upgrade
```

## Deprecated configuration keys

A renamed or removed key of `piloop.toml` keeps working for at least one minor release. Each use shows a
`PiloopDeprecationWarning` with the file, the line, the new key and the release that removes the old one. The
[configuration reference](/reference/configuration#deprecated-keys) and the
[changelog](https://github.com/hiloopai/piloop/blob/main/CHANGELOG.md) list them.

## What is stable

Before 1.0, a minor release may break these, and the changelog says so:

- The `piloop` CLI: its commands and their flags.
- The keys of `piloop.toml`.
- The contract of the [evaluate command](/concepts/campaigns#the-evaluate-command).
- The [database schema](/reference/schema), as `piloop sql` shows it.

`piloop.capabilities` is the stable plugin API. Other `piloop.*` imports can change in any release.

## Upgrading to the next release

### A run claims any number of ideas

A run may claim ideas, and propose its own, as many times as its implementer wants. The table `run_claims` (`run_id`,
`idea_id`, `attempt`, `claimed_at`) holds the claims, and replaces `runs.idea_id` and `runs.attempt`. The migration
moves each run's claim there, and a downgrade refuses a database where a run claimed more than one idea.

- A query that joined a run to its idea joins its claims:

  ```sql
  SELECT r.id, i.title FROM runs r JOIN run_claims c ON c.run_id = r.id JOIN ideas i ON i.id = c.idea_id;
  ```

- The table `submissions` (`run_id`, `candidate_id`, `idea_id`, `event_id`, `submitted_at`) holds each submission,
  for the claim that it was for, with its `run.submitted` event. Join an idea to what was submitted for it through it:
  one candidate may be submitted for several ideas, by several runs. What settles a claim, what waits for a score and
  what a worker hears all read it. `candidates.idea_id` names the claim that a candidate was made for, or last
  submitted for.
- `piloop submit --idea <id>` names the claim that a version is for. By default it is the run's newest claim.
- `--base` of `piloop idea claim` and `piloop idea propose` works only before the run's first submission.
- When the run ends and its submissions have their scores, each claim settles on its own: its idea is `done` once a
  submission for it has a score, whatever the run's end, and `open` again otherwise.
- A plugin's campaign type: `CampaignType.settle(s, claim, end, submissions)` settles one claim, with the run's
  submissions for its idea, in place of `settle(s, run, end, last)`.
- `persistent = true` on a role that does runs keeps each implementer working until its `timeout`: it claims, asks
  for or proposes ideas as it wants, and the next run of its slot starts from the best. It is off by default.

## Upgrading to 0.8.0

### Upgrade from 0.7

0.8.0 migrates a database from 0.7's heads or newer: a 0.6 home upgrades through 0.7 first, as
[Upgrade one release at a time](#upgrade-one-release-at-a-time) says.

- The upgrade rebuilds the tables whose ids leave the database (events, comments, runs, candidates, ideas and
  measurements) so that an id is never used again. Its time grows with those tables: on a small home it takes under a
  second.
- It copies each measurement's per-unit results from `<home>/units` into the CAS, and the server's owner id from
  `<home>/owner` into the database. It leaves both, which nothing reads any more: delete them once you will not go
  back to 0.7.
- On Linux, the upgraded daemon serves its API from processes beside it: `[daemon] api_processes = "auto"`, half the
  cores up to 8, about 130 MB each. The count follows the daemon's CPU affinity, not a container's CPU limit: in a
  container, set `api_processes` to what its limit allows. Set `api_processes = 0` in `config.toml` to serve from the
  daemon alone, as 0.7 did. With `[plugins.executor] relayed_calls` below that count, the daemon does not start, and
  says which key to set.

### Infrastructure failures count per task

A submission may carry a one-line `TASK` file at its root. `[evaluation] stop_after_tries` failures in a row for one
task hold only that task's evaluations, and `piloop candidate remeasure` on one of its candidates releases them.
Submissions without a `TASK` file share one count, and at the limit the whole campaign pauses, where 0.7 paused only its
measurements: `piloop resume` starts it again.

### `piloop sql` has limits

A statement that runs longer than `[sql] statement_seconds` (5 s by default, in `config.toml`) is interrupted and
changes nothing. A wait for the write lock does not count. Raise the limit for a long report.

### A plugin

- A provider's routes come from `Serves.routes(host) -> Routes`, which each process that serves the API calls.
  `Contribution.router` is gone, `LineageProvider.contribution` is `LineageProvider.routes`, and
  `Executor.configure` is gone: the leases read the live limits of the pools themselves.
- A network binds in `Network.bind()` and serves on the bound socket in `Network.listener(sock)`.
- A VCS provider implements `Repository.merge(ours, theirs, summary)`, which the `accumulating` type calls.
- A CAS provider may answer `shared()`: whether every host that serves the home reaches its blobs.

### The keys that 0.7 deprecated are removed

The keys that 0.7 deprecated now fail. One line names each key, the line of the file that sets it and what to do, such
as `config.toml:3: delete [agents] wake_budget: piloop 0.8.0 removed it`. Delete them from each `piloop.toml` and from
`config.toml`; `piloop doctor` names each one. Delete `[agents] wake_budget` from `config.toml` before you upgrade: no
command but `piloop --version` runs with it, so `piloop upgrade` stops and the old daemon keeps running. The database's copies need nothing: 0.7's revisions already took these keys out of them.

| Removed | Write |
|---|---|
| `scoring` of `[evaluator]` | nothing: piloop scores what an implementer submits |
| `[plugins.memory]` | nothing: research memory is removed |
| `"lessons"` in `[plugins.section] use` or in a role's `sections`, a `[plugins.section.<name>]` of `provider = "lessons"` | nothing |
| `[agents] wake_budget` of `config.toml` | nothing: `piloop wake` is removed |

## Upgrading to 0.7.0

### Upgrade from 0.6

0.7.0 migrates a database from 0.6's heads or newer: a 0.5 home upgrades through 0.6 first, as
[Upgrade one release at a time](#upgrade-one-release-at-a-time) says. The upgrade rewrites the copy of each
`piloop.toml` that the database stores: it takes out every key in the tables below, and a campaign that scored at run
end scores what its implementers submit.

### Removed keys

The keys that 0.5 and 0.6 deprecated now fail as unknown keys, with a link to the configuration reference. Delete
them from each `piloop.toml` and from `config.toml`, or write them as this table says:

| Removed | Write |
|---|---|
| Each key of [Removed features](#removed-features) of 0.6.0: the research, watchdog, scout and orchestrator roles, the trigger tables, sweeps, seeds, the `idle_queue`, `yields`, `incidents`, `reported` and `research_commands` sections, `[plugins.stop_rule] while_held` | nothing |
| `[plugins.verdict_rule]`, a role's `follow_head`, a metric's `repeats`, `[plugins.section.judging]` | nothing: the pool replaces verdicts |
| `"judging"` in a role's `sections` | `"scoring"` |
| A role's `finding_grace`, in `piloop.toml` or `config.toml` | `end_grace` |
| `share` of `[tracks.<name>]` | nothing |
| `grace` of `[plugins.escalation]` | nothing: every escalation reaches a human at once |
| `[agents] relay_wait` and `relay_deadline`, `[evaluation] wake_after_tries` of `config.toml` | nothing |

`[evaluator] scoring` loaded with a warning in 0.7 and did nothing: 0.8.0 removes it
([Upgrading to 0.8.0](#upgrading-to-0-8-0)).

### Run-end scoring is removed

piloop scores only what an implementer submits (`piloop submit`). Each other version of a run is a `skipped`
candidate, never measured. `[evaluator] scoring = "run_end"`, which 0.6 kept for the campaigns that 0.5 stored, is
gone, and so is the key: delete `scoring` from `[evaluator]`. piloop no longer reads the `Piloop-Eval: skip` and
`Piloop-Note` trailers of a commit: a commit that is not submitted is never measured, and a note goes on the board as
a `note` comment.

### The evaluate command reports a status

The result line of the [evaluate command](/concepts/campaigns#the-evaluate-command) must carry `status`, and the
primary metric as `score`. 0.6 still took 0.5's line; 0.7 refuses it as a bad result, which is a crash:

| 0.5's line, refused | Write |
|---|---|
| `{"metrics": {"bytes": 3688775, "seconds": 0.82}}` | `{"status": "ok", "score": 3688775, "direction": "lower", "metrics": {"seconds": 0.82}}` |

A rung of the ladder still reports its metrics alone.

### The API and the CLI

- An inbox item and a comment show `acks`, one for each party that acknowledged it. `acked_at` and `acked_by` are
  gone: read the ack of the `human` party, or of your role.
- `piloop submit` takes no `--wait`: it returns at once, as in 0.6. A worker's relay from before 0.6 passed it.

### A plugin

- `Surface.SWEEP` is gone: write `Surface.ORCHESTRATOR`.
- A vcs provider's `Version` has no `skip` and no `notes`, and the prompts have no `{vcs:mark}` part.

### The orchestrator role is removed

piloop launches no orchestrator of its own. Every escalation reaches your notifiers at once, and the coding agent that
you talk to is the [orchestrator](/concepts/orchestrator), with the `piloop-operate` skill. A plugin can still add a
role that starts its own agents ([Roles](/plugins/agents#roles)). Its keys are in
[Removed keys](#removed-keys): `[plugins.role.orchestrator]`, `[plugins.escalation] grace`,
`[evaluation] wake_after_tries` of `config.toml`, and the `incidents`, `reported` and `research_commands` sections.

`piloop inbox wait` and `GET /v1/inbox/news` no longer return news of kind `anomaly_requested`.

### An escalation takes one answer

Each party, such as the people or the orchestrator, acknowledges an inbox item for itself. The table `acks` holds one
row for each party that acknowledged an item, and replaces `comments.acked_at` and `comments.acked_by`. A `piloop sql`
query on those columns fails: read `acks`. The API shows `acks` too: see [The API and the CLI](#the-api-and-the-cli).

- An answer takes an item out of every inbox. An escalation takes one answer: a second one is refused, with the first.
- An orchestrator's ack no longer stops a notifier: it sends what no person acknowledged.

### Research memory is removed

The lessons, the documents and the orchestrator's journal are gone. The orchestrator keeps its notes in the event
stream instead: a `note` comment on the campaign, which the `piloop-operate` skill reads back when a session starts.

- The migration drops the `lessons`, `documents`, `documents_fts` and `journal` tables with their rows, and archives
  nothing. The backup that the upgrade writes first still has them: copy out what you need before you upgrade.
- `piloop wake`, `piloop journal` and `POST /v1/campaigns/{campaign}/journal` are removed. The answers of
  `POST /v1/campaigns` and `POST /v1/campaigns/{campaign}/sync` no longer have `documents`.
- The `lessons` section, the SQL function `blake3()` and the memory capability (`MEMORY`, `MemoryProvider`,
  `LocalMemory` and `Synced` in `piloop.capabilities`) are removed.

Its keys, `[plugins.memory]`, the `lessons` section and `[agents] wake_budget` of `config.toml`, loaded with a warning
in 0.7 and did nothing: 0.8.0 removes them ([Upgrading to 0.8.0](#upgrading-to-0-8-0)).

### A cancel stands, and keeps the origin

`piloop eval cancel` no longer makes a run's candidate `skipped`. It keeps its origin, and stays in the pool of every
evaluator that scored it. The cancel stands under the evaluator that it cancelled: the daemon does not confirm the
candidate, score it on the sealed split, or measure it again as the baseline or the best before an evaluator change.
`piloop candidate remeasure` asks for it again. The table `cancels` holds each cancel. The migration gives each
candidate that 0.6.0 made `skipped` for a cancel its origin back.

### A remeasure gets the evaluations that it asks for

`piloop candidate remeasure --repeats 5` gets 5 evaluations of its own. An evaluation of the candidate that ran when
you asked, or `piloop measurement add`, no longer ends the request: the candidate's mean includes it, and the request
waits for its own evaluations. The column `evaluations.ask` names the request that an evaluation is for.

A full disk while piloop stores a campaign's linked inputs is no longer the candidate's crash. It is an infra error, as
in the evaluate command: the evaluation runs again after `[evaluation] infra_retry`, and after `stop_after_tries`
failures in a row for the same committed `TASK` ID, that task's evaluations pause. Retry the task with
`piloop candidate remeasure <id>`. Submissions without a task ID share one count and pause the entire campaign at
the same limit. A tagged campaign also pauses when all tasks in its registered `TASKS.txt` are held, or when an
inventory fact source reports `available_eval_images = 0`. Restore an eligible evaluation, then run `piloop resume <campaign>`.

### An agent that took a few turns worked

An agent whose harness counted more than `[agents] startup_turns` turns (3 by default) worked, however soon it ended.
It is not `never_worked`, and its run is an attempt. Below that number, `startup_seconds` decides as before.

### An agent's deadline and token

- `agent_sessions.deadline` is when its timeout ends the agent, stored at its launch. The agents that run at the
  upgrade have none: they get no wrap-up message before their timeout.
- An agent's token ends with its session. The migration deletes the tokens of the agents that ended.
- A stop or a cancel ends a starting agent at once. The id of a deleted agent session is never used again.

### The database refuses impossible rows

New CHECKs refuse a `piloop sql` write that leaves a row in an impossible state. The migration repairs the rows that
an earlier write broke, and logs how many:

| Table | A write is refused when |
|---|---|
| `campaigns` | A pause has no owner (`paused_by`, new), an owner has no pause, an active campaign has a `stopped_reason`, a stopped or retired one has none, or a retired one is paused. |
| `agent_sessions` | An ended agent has no `ended_at`, an open one has one, or a `never_worked` one has no `error`. |
| `evaluations` | A cancelled evaluation is not running. |

## Upgrading to 0.6.0

### Upgrade from 0.5

0.6.0 migrates a database from 0.5's heads or newer: a 0.4 home upgrades through 0.5 first, as
[Upgrade one release at a time](#upgrade-one-release-at-a-time) says.

### Removed keys

The keys that 0.5 moved now fail as unknown keys. Write them as the 0.5 notes say:

| Removed | Write |
|---|---|
| `[daemon] startup_relaunches` of `config.toml`, `PILOOP_DAEMON__STARTUP_RELAUNCHES` | `[plugins.role.implementer] startup_relaunches` |
| `[agents] finding_grace` of `config.toml` or `piloop.toml`, and its variables | `[plugins.role.implementer] end_grace` |
| `[agents] wrap_up_lead` of `config.toml`, `PILOOP_AGENTS__WRAP_UP_LEAD` | `[plugins.role.implementer] wrap_up_lead` |

A campaign that 0.4 stored, and that no `piloop init` stored again since, gets no notifiers from `config.toml`: run
`piloop init` on it to store its notifiers.

### Removed features

Their keys still load, with a warning, until 0.7.0, and do nothing. What they wrote stays in the database.

| Removed | Its keys |
|---|---|
| The research role, and its `low_water` and `stalled` triggers. Each worker proposes its own idea when the board has none for it. | `[plugins.role.research]`, `"low_water"`, `"stalled"` |
| The watchdog role. | `[plugins.role.watchdog]` |
| The scout role. Its `techniques` table stays readable. | `[plugins.role.scout]` |
| Sweeps: a sweep's timer, its closing review at the stop, its incident and routine prompts, and the low-yield alarm. | `"cron"`, `"stopped"`, `"low_yield"`, `"dead_at_startup"`, a role's `interval`, `incident_prompt` and `routine_prompt`, `[plugins.stop_rule] while_held`, the `yields` section |
| Sweeps of your own: a role of your own does runs. | `[plugins.role.<name>]` without `runs = true`, a `[plugins.trigger.<name>]` of `provider = "sql"` |
| The `leaking_funnel` and `seed` triggers, and seeds: an idea is open on the board from the start. | `"leaking_funnel"`, `"seed"`, `files = "seeds"`, `[plugins.section.pack] seeds` |
| Ideas that implementers file for other runs. A hunch for another run goes in a note on the board. | `files` and `plan_words` of a role that does runs |
| The caps on the orchestrator's ideas. | `files`, `plan_words` and `max_ideas` of `[plugins.role.orchestrator]` |
| The rules that gave ideas to runs, and ideas that wait for a review. | `takes`, `explore_every`, `recovery_requeues`, `idle_alert` |
| The trigger tables, `quiet_seconds` included. | `[plugins.trigger.<name>]` |
| The `idle_queue` section. | `"idle_queue"` in a list of sections, `[plugins.section.idle_queue]` |

A package's own role, trigger or section of one of these names keeps its table and its keys.

### A plugin's role

`piloop.capabilities` no longer has `SweepRole`, `Sweep` or `Files`, and a role has no `ideas_line` or `refuses_idea`.
A plugin's role is a subclass of `ImplementerRole`, which does runs, or of `StartsItsAgents`, which decides when its
agents start: it answers each pass over a campaign with its requests (`request`), says whether it wakes while the
campaign is paused, held or stopped (`wakes_while`), and launches its agents (`launch`). `Quiet` comes
from `piloop.capabilities`.

### The board

An idea is `open`, `claimed`, `done` or `dropped`. The migration renames each status:

| 0.5 | 0.6 |
|---|---|
| `seed`, `proposed`, `ready` | `open` |
| `scheduled` | `claimed` |
| `done` | `done` |
| `parked`, `rejected` | `dropped` |

- `piloop idea status` takes `open` or `dropped`. Only a run makes an idea `done`.
- `piloop idea seed` and `piloop idea develop` are removed: use `piloop idea add`. Its `--family`, `--proposed` and
  `--supersedes` are removed.
- `piloop idea link` takes only `after`. An `after` link holds an idea until its prerequisite is `done` or `dropped`.
- `idea: <title>` in a notifier's thread adds an open idea. A notifier plugin answers it with `AddIdea`, not
  `FileSeed`.

### Claims

The daemon gives no idea to a run. For each free slot it starts a run from the best, and the implementer claims one
open idea (`piloop idea claim`), or proposes one and claims it (`piloop idea propose`). The idea is `done` after a
finished run whose last candidate has a score, and `open` again otherwise.

- A run's `idea_id` and `attempt` are null until its implementer claims an idea.
- `piloop idea base`, and `--harness` and `--base` of `piloop idea add`, are removed. The migration deletes
  `ideas.base_candidate_id`, `ideas.harness` and `ideas.max_runs`. A run starts from the best, or from the candidate
  that `--base` of `piloop idea claim` or `piloop idea propose` names.
- `[tracks.<name>] share` is removed: workers claim any open idea.

### Run ends and messages

An implementer's clean exit ends its run: `finished` when it submitted a version, `gave_up` otherwise.
`piloop run end submitted` or `piloop run end gave_up` ends it before the session exits.

- The `finding` kind is removed: a worker reports in a `note` on its idea. Old findings stay readable.
- No kind of comment does anything when it is written: the migration deletes `comment_kinds.after_end`.
- `finding_grace` is `end_grace`. The migration renames it in each stored config.
- An escalation holds no run: the migration makes each `awaiting_answer` run `failed`.
- Only a `message` reaches a running agent, on the agent, its run or its idea. Every harness hears it at its next
  `piloop` command. A `note` stays on the board.
- A plugin that names `escalation` or `decision` imports `ESCALATION` and `DECISION` from
  `piloop.plugins.escalation.kit.kinds`, not from `CommentKind`.

### An agent that never worked ends `never_worked`

An agent whose job did not start, or that ended within `startup_seconds` and left nothing, ends `never_worked`, not
`exited` or `killed`. After 0.6.0, an agent that took more than `startup_turns` turns worked: see
[An agent that took a few turns worked](#an-agent-that-took-a-few-turns-worked). Its `error` says why, also when it exited 0. A query that counts ended agents with
`state IN ('exited', 'killed')` adds `'never_worked'`. Rows that ended before the upgrade keep their state.

- A wrap-up no longer hides such an end: an implementer told to wrap up as it starts, that leaves nothing, never
  worked, and its run is no attempt.
- A run is queued again after a failed start only when its campaign would launch it now. While the startup breaker
  holds, within the wrap-up lead, or while the campaign is paused, the run ends `not_started` at once and frees its
  slot.
- When launches resume, the daemon acknowledges the startup breaker's escalation.

### The evaluate command reports a status and a score

| 0.5 | 0.6 |
|---|---|
| `{"metrics": {"bytes": 3688775, "seconds": 0.82}}` | `{"status": "ok", "score": 3688775, "direction": "lower", "metrics": {"seconds": 0.82}}` |
| exit 1 | `{"status": "crash", "feedback": "<why>"}`, or exit 1 |
| exit 1 on a rate limit | `{"status": "infra_error", "feedback": "<why>"}`: no score, run again later |

A line without `status` still reads as `ok`, with the primary among `metrics`, until 0.7.0.

### Implementers submit

| 0.6 default | What it does | 0.5's value |
|---|---|---|
| `[evaluator] scoring = "submit"` | An implementer scores a commit with `piloop submit`. Other commits are `skipped`. | `"run_end"` |
| `[evaluator] noise_runs = 3` | The baseline, and each candidate whose first score beats the best, get 3 evaluations. | `1` |

A campaign that 0.5 made keeps 0.5's values in its stored config. `piloop campaign sync` or `piloop init` reads its
`piloop.toml` again, and gives it the 0.6 defaults. To keep 0.5's noise runs, put them in `piloop.toml`
(0.7.0 removes run-end scoring):

```toml
[evaluator]
noise_runs = 1
```

### `piloop submit` returns at once

`piloop submit` prints the candidate and returns. Where it stands reaches the implementer as a `[piloop]` message.
`--wait` is ignored until 0.7.0. The route `GET /v1/submissions/{candidate}` is removed: read
`GET /v1/candidates/{candidate}`. `[agents] relay_wait` and `relay_deadline` of `config.toml` are dropped with a
warning.

### The pool replaces verdicts

piloop scores every candidate into the campaign's [pool](/concepts/pool), and the best is a query. There is no
verdict, head, bar, trunk or rebase.

- `[plugins.verdict_rule]`, `[[metrics]] repeats` and a role's `follow_head` are dropped with a warning. A
  [best rule](/plugins/rules#best-rules), `[plugins.best_rule]`, says which confirmed candidate may be the best.
- A guardrail's `margin` and `fraction` compare with the baseline's value.
- The section `judging` is `scoring`.
- `candidates.verdict`, `cause`, `verdict_by`, `verdict_reason` and `track`, and `measurements.pair_id`, are deleted.
  Each verdict stays in a `candidate.verdict` event. `candidates.excluded_reason` and `excluded_by` are new.
- `piloop candidate verdict` is removed: use `piloop candidate exclude <id> --reason "<why>"`.
- `piloop candidate remeasure` never refuses: the mean includes the new evaluations, and the best follows.

The facts of the `optimization` source are renamed:

| 0.5 | 0.6 |
|---|---|
| `head` | `best` |
| `without_keep` | `without_best` |
| `keeps` | `new_bests` |
| `<name>_since_keep` | `<name>_since_best` |
| `per_keep` | `per_best` |

The API changes so:

| 0.5 | 0.6 |
|---|---|
| `CampaignState.head`, `kept` | `CampaignState.best` (one `TrackBest` per track), `new_bests` |
| Inbox news of kind `verdict` | Of kind `score`, with `told` |
| The submit answer's `verdict` and `score` | `told`: where it stands, null until the daemon scored it |
| `CandidateView.label`, `cause`, `verdict_reason` | `CandidateView.origin`, `excluded_reason` |

A plugin imports `BestRule`, `Case`, `Scores`, `Criterion` and `Baseline` from `piloop.capabilities`. `VerdictRule`,
`Judgement`, `Outcome`, `Node`, `Trunk`, `Imported`, `Rebase`, `Noise`, `Bootstrap` and `Bar` are removed. The events
`candidate.judged`, `candidate.rebased`, `candidate.noted`, `candidate.rejudge_requested`, `candidate.rejudge_failed`,
`run.verdict_told`, `run.head_replaced` and `candidate.verdict` are retired. The new ones are `candidate.scored`,
`run.score_told`, `run.base_chosen` and `candidate.excluded_reason`.

### A cancelled evaluation records nothing

`piloop eval cancel` records no measurement. In 0.6.0, a run's candidate is `skipped`, not a `crash`. After 0.6.0 it
keeps its origin: see [A cancel stands, and keeps the origin](#a-cancel-stands-and-keeps-the-origin).

### The implementer's brief is shorter

The implementer's brief no longer shows the `queue` section or the `database` guide. `piloop schema database` prints
the guide. To keep them, list them in `[plugins.role.implementer] sections`.

### New defaults

| Key | 0.6 | 0.5 |
|---|---|---|
| `[plugins.role.implementer] max_concurrent` | 2 | 4 |
| `[plugins.role.implementer] timeout` | 3600 | 1800 |
| `[plugins.harness] use` | `["claude", "codex"]` | `["pi"]` |

A `piloop.toml` that sets a key keeps its value. To keep pi, set `use = ["pi"]`.

### Only a stop rule or a person stops a campaign

`piloop campaign stop` by an agent is refused, and the agent escalates a stop instead. After 0.6.0, piloop has no
orchestrator role: see [The orchestrator role is removed](#the-orchestrator-role-is-removed).

### One worker on a home

A second `piloop worker` on one `PILOOP_HOME` exits and says why. The daemon's own worker uses its home too, so a
`piloop worker` on the daemon's home is refused, and a daemon does not start on a home where a worker runs. Give each
worker its own home.
