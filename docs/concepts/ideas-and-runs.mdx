title: Ideas and runs
description: An idea is one thing to try, on the campaign's board. A run is one implementer's attempt at the idea that it claimed.
---

An **idea** is one thing to try:

```bash
piloop idea add enwik8 "Model the text with an order-2 context mixer" \
  --hypothesis "lzma does not model the next byte from the bytes before it"
```

```text
idea#2 open p2: Model the text with an order-2 context mixer
```

The ideas of a campaign are its **board**. The board lists the `open` ideas, most urgent first: priority 0 is urgent,
4 is someday, and 2 is the default. Each implementer **claims** one of them. To change a status, give the reason:

```bash
piloop idea status 2 dropped --reason "idea#1 tests the same mechanism"
```

```text
idea#2 open → dropped: idea#1 tests the same mechanism
```

| Status | Meaning |
|---|---|
| `open` | On the board. An implementer can claim it, unless an `after` link holds it. |
| `claimed` | A run claimed it. The run is open, or its commits wait for their verdicts. |
| `done` | Its run finished and its commits are judged. |
| `dropped` | Off the board: by hand, after a cancel, or when its run ended on an open escalation. `open` puts it back. |

## Who adds ideas

| Who | What it adds |
|---|---|
| You, the orchestrator | Ideas. You change the priority and status of any idea. |
| Research | Ideas, when the board runs short. |
| Watchdog | Nothing. Its findings say what it would try. |
| Implementer | One idea of its own, which it claims at once (`piloop idea propose`). It files none for others. |
| Daemon | Adds an idea when a merge conflicts. |

`piloop idea add enwik8 "<title>" --after 1` holds the idea until idea 1 is `done` or `dropped`. Then a worker can
claim it, and its run starts from the head, which holds what idea 1 kept.

`piloop candidate import enwik8 <commit>` makes any commit a **reference**, such as a branch. To take its change, add
an idea that names it.

## Runs

A **run** is one implementer's session. For each free implementer slot, the daemon makes a worktree of the head,
writes the brief (your `brief.md`, the board and the state of the campaign), and starts the implementer, on the next
harness of `harnesses`. The implementer first takes one idea:

```bash
piloop idea claim 2
piloop idea propose "Model the text with an order-3 context mixer" --hypothesis "order 2 leaves context unused"
```

The run tries that idea only. The implementer commits, also when the idea did not work.

The run ends when the implementer exits, at its `timeout`, or a minute after it writes its `finding`. To give it more
time, use [`piloop run extend`](/reference/cli#piloop-run-extend). Then the daemon scores each new commit. What the implementer left uncommitted becomes a `recovered` commit, which is never measured.
If git refuses that commit, the run fails, and an `agent_session.work_unsaved` event holds the changes as a patch.
Restore them in a checkout of the implementer's last commit with `piloop cas get <blob> | git apply`.

The claim ends with the run:

| How the run ended | What happens to the idea |
|---|---|
| It finished | `done` once its commits are judged. |
| It failed, timed out or was stopped | Back to `open`, for another implementer. |
| It was cancelled | `dropped`. |
| It stopped on an open escalation | `dropped`. Answer with a `decision` comment, then set the idea `open`. |

An implementer that never started to work claimed nothing: its run is queued again, up to two times.

## Talk to a running implementer

A `note`, `finding` or `decision` comment on a running run, or on its idea, reaches the implementer within seconds. It
gets the first line, up to 200 characters. A comment that cannot reach it goes into the next run's brief.

An implementer can add a trailer to a commit message:

| Trailer | Effect |
|---|---|
| `Piloop-Note: <why>` | The commit regressed, but is worth starting from. |
| `Piloop-Eval: skip` | The commit is scaffolding: it is not measured. |
