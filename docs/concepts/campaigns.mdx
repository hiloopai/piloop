A **campaign** is a git repo, an **evaluate command** that scores its code, and the metrics to improve. This is the
`piloop.toml` of the enwik8 example, without its limits:

```toml
name = "enwik8"
evaluate = ["uv", "run", "python", "evaluate.py"]
link = ["data", ".venv"]

[plugins.harness]
use = ["claude"]

[plugins.harness.claude]
model = "claude-opus-5-5"

[[metrics]]
name = "bytes"
direction = "lower"
role = "primary"

[[metrics]]
name = "seconds"
direction = "lower"
role = "guardrail"
margin = 60
floor = 120
```

`brief.md`, next to it, tells the agents what to improve and what not to touch, in at most 400 words. `piloop init`
registers the campaign and stores a copy of `piloop.toml` for the daemon: run it again after each edit.

## The evaluate command

piloop runs the command at the root of a clean worktree of each commit. The command appends one JSON line, its
**result**, to the file that `$PILOOP_RESULT_FILE` names. When the variable is not set, it prints the line:

```python
import json
import os

def report(result):
    line = json.dumps(result)
    if path := os.environ.get("PILOOP_RESULT_FILE"):
        with open(path, "a") as f:
            f.write(line + "\n")
    else:
        print(line)

report({"status": "ok", "score": compressed + compressor_size, "direction": "lower",
        "metrics": {"seconds": round(cpu_seconds, 2)}})
```

```bash
uv run python evaluate.py
```

```text
{"status": "ok", "score": 3688775, "direction": "lower", "metrics": {"seconds": 0.82}}
```

| Key | Holds |
|---|---|
| `status` | `ok`, or why nothing counts: `crash` or `timeout` when the candidate failed, `infra_error` when something else failed. |
| `score` | With `ok`: the value of the primary, the first metric with `role = "primary"`. |
| `direction` | With `ok`: `higher` or `lower`, as the primary's `direction` says. |
| `metrics` | A number for each other metric, by its name. Each guardrail is required. A watch metric is optional. |
| `feedback` | Optional: one line on what the evaluation saw. piloop keeps it on the measurement's event. It never sends it to an implementer. |
| `units` | Optional: the [per-unit results](#per-unit-results). |
| `evidence` | Optional: files of the worktree that explain the result, by a label, such as `{"errors": "out/errors.md"}`. piloop keeps them with the evaluation's logs. |

A missing or unknown metric, a second line, a non-zero exit after `ok`, or a run past `evaluate_timeout` seconds
makes the commit a `crash`. Give the reason on stderr or as `feedback`. Fix the seeds and the splits, so that the same
code gets the same score.

An `infra_error` is never a score. Report it for a fault that is not the candidate's, such as a rate limit or a lost
GPU. The evaluation waits in `piloop eval queue` and runs again later. After `[evaluation] stop_after_tries` failures
in a row (3 by default, in `config.toml`), piloop holds evaluations of the affected task and escalates.
In a campaign with independent tasks, commit a short, single-line task ID in a regular file named `TASK` at the
root of each submission. Candidates with the same ID share a failure count within the campaign. A completed
evaluation of that task breaks the streak. Once held, new evaluations of the task wait while other tasks continue.
After fixing the cause, run `piloop candidate remeasure <id>` on a candidate of the held task to retry it and release its siblings.

Submissions without a usable `TASK` ID share one failure count per campaign. For example, if three different untagged
ideas each hit the same broken evaluator once, the third consecutive infrastructure failure pauses the entire campaign
at the default limit. Queued evaluations wait, including tagged ones. Work already running can finish. After fixing
the evaluator, run `piloop resume <campaign>` to resume with a fresh count.

`[evaluator] dev` names a fast check that the implementers run in their own checkouts. piloop never runs it:

```toml
[evaluator]
dev = ["uv", "run", "python", "evaluate.py", "--quick"]
```

<Warning>
  piloop runs the evaluate command from the commit that it measures. An implementer that edits the command changes its
  own score. Tell the implementers in `brief.md` not to edit it or the data.
</Warning>

## Metrics

| `role` | How [the best](/concepts/pool#the-best) uses it |
|---|---|
| `primary` | The metric to improve. One per campaign, or one per [track](/concepts/pool#tracks). |
| `guardrail` | The best may be worse than the baseline by at most its tolerance, and never past `floor`. |
| `watch` | Recorded only. This is the default. |

A **tolerance** is a `floor`, plus one of `margin` and `fraction`. `margin` is in the metric's units: `margin = 60`
allows 60 s more than the baseline. `fraction` is a share of the baseline's value: `fraction = 0.10` allows 10% more.

### Ratio metrics

A primary or a guardrail can be the **ratio** of two metrics that the evaluate command reports. piloop computes it
from the means of the parts:

```toml
[[metrics]]
name = "solved"
direction = "higher"
role = "primary"

[[metrics]]
name = "cost_usd"
direction = "lower"

[[metrics]]
name = "cost_per_solved"
direction = "lower"
role = "guardrail"
ratio = { numerator = "cost_usd", denominator = "solved" }
fraction = 0.05
```

The evaluate command reports `solved` and `cost_usd`, never `cost_per_solved`.

## The evaluation ladder

An evaluation ladder stops a bad candidate before the full panel. Each `[[ladder]]` table is a **rung**: a cheaper
result that the evaluate command reports first, and a `stop` that ends the climb there:

```toml
[[ladder]]
name = "screen"
stop = { accuracy = { margin = 0.05 } }
```

The command reports the rung, then extends it into the full panel:

```python
done = score(PANEL[:50])
report({"rung": "screen", "metrics": {"accuracy": sum(done) / len(done), "cost": 0.05}})
done += score(PANEL[50:])
report({"status": "ok", "score": sum(done) / len(done), "direction": "higher", "metrics": {"cost": 0.45}})
```

A commit scored 0.2 at the screen, where the best scored 1, so piloop ended the command:

```bash
piloop sql "SELECT candidate_id, rung, stopped, metrics FROM measurements"
```

```text

```

- `stop` takes a guardrail's keys. Past `floor`, or worse than the best at the same rung by more than `margin` or
  `fraction`, the climb stops.
- Only the first evaluation of a run's commit can stop. The baseline, confirmations and remeasures climb every rung.
- Report each line's own cost: piloop sums the rows.
- A rung with its own `evaluate` command runs that command first. Such rungs come first in `[[ladder]]`.
- `piloop candidate show` prints each rung's values. A stopped candidate has no score.

## Per-unit results

A metric that is a sum over units, such as test examples, can report each unit's part:

```json
{"status": "ok", "score": 0.0112, "direction": "higher", "units": {"accuracy": {"test-0001": 0.0056, "test-0002": 0.0, "test-0003": 0.0056}}}
```

The parts must sum to the metric's value, within 0.1%. The score's units go under the primary's name. piloop stores
them in `~/.piloop/units/`, where no agent sees them. No score reads them.

## Evaluators

An **evaluator** is the evaluate command, `link`, the ladder's rungs, and the names and directions of the primaries
and guardrails. A change to one of them makes a new evaluator at the next `piloop init`. A change to a margin, a floor,
a `stop` or a watch metric does not.

piloop never compares scores of two evaluators. Under a new evaluator, it measures the baseline and the best again, and
new runs wait until both have a score. An evaluation that waits moves to the new evaluator. One that runs finishes
under its own, and `piloop eval queue` marks it `(retired)`. Other candidates keep their old scores until you measure
them again:

```bash
piloop candidate remeasure 2
```

## Reopen, fork and retire

```bash
piloop campaign stop enwik8
piloop campaign reopen enwik8 --reason "one more round of runs"
piloop campaign fork enwik8 --name enwik8-lzma
piloop campaign retire enwik8 --reason "tried every idea"
```

- **Reopen** sets a stopped campaign active again, once its stop is over. The runs, hours and tokens of its stop rule
  count from the reopen. When the rule would stop it at once, change the rule and run `piloop init`: it reopens a
  stopped campaign whose stop rule changed, the same way.
- **Fork** makes a new campaign from the best of another one, or from the version that `--at` names. It takes the
  source's `piloop.toml` and its repo, so it sees the ideas of every campaign on the repo. It starts with no ideas of
  its own.
- **Retire** ends a stopped campaign for good and frees its name. Its rows stay: `piloop status 3`. Its files move
  to the [archive](/concepts/archive), and `piloop restore 3` writes them back. To go on, fork it.

A server that cloned a campaign's repo takes its new commits with `piloop campaign sync enwik8`. It reads
`piloop.toml` again, and the candidates and their scores stay. To try the new code, import it as a candidate
(`piloop candidate import enwik8 origin/main`).

When a campaign's checkout is gone from the disk, `piloop status` shows its files as `missing`, and fork, reopen and
sync refuse with the path that is gone.

## Files

| Path | What it is |
|---|---|
| `link` paths | Paths that git ignores, such as `data` or `.venv`, put into every worktree read-only. |
| `workspace/` | A directory that every agent of the campaign shares, for notes, results and plots. It is never committed. |
| `scratch/` | A directory in each agent's checkout for what a run can make again, such as data samples and build outputs. It is in no version, and goes with the checkout. |
| `refs/piloop/<campaign>/` | A git ref for each commit of each run, such as `refs/piloop/enwik8/r1/0`. |
| `~/.piloop/runs/`, `~/.piloop/agent_sessions/` | The briefs, logs and transcripts of the agents. |

The database holds the ideas, runs, candidates, measurements and comments. Read it with `piloop sql`.
