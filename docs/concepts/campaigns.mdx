A **campaign** is a git repo that piloop knows about. It has two files at its root and one command:

- `piloop.toml`: the configuration. See the [configuration reference](/reference/configuration).
- `brief.md`: the instructions that every agent reads before its task.
- The **evaluate command**: the program that scores the code, such as the template's `evaluate.py`. The `evaluate` key
  in `piloop.toml` names it.

`piloop init` registers the campaign in the piloop database, `~/.piloop/piloop.db`, with a copy of `piloop.toml`. The
daemon uses that copy, so run `piloop init` again after you edit the file. Set `PILOOP_HOME` to use another
directory. One database holds every campaign, and one daemon serves them all.

## The evaluate command

The evaluate command is the referee. piloop runs it in a clean worktree of each commit that an implementer makes. Two
commits are not measured: a commit marked `Piloop-Eval: skip`, and a commit whose tree the current evaluator has
measured already. The command must:

- Run from the root of the repo.
- Print one line `METRIC <name>=<value>` on stdout for each metric in `piloop.toml`. Other output is ignored, and so is a
  line with no name or with a value that is not a finite number.
- Exit with status 0. A non-zero exit, or a run longer than `evaluate_timeout` seconds, makes the candidate a
  `crash`. Print the reason on stderr.

For example:

```text
METRIC bytes=3692731
METRIC seconds=0.52
```

Make the command deterministic: fix the seeds and the data splits. Make sure that an implementer can change the score only
through the code that it is supposed to change. Tell the implementers in `brief.md` which files they must not edit, such as
the evaluate command and the data. piloop runs the evaluate command from the commit that it measures, so an implementer that
edits it changes its own score.

### Stop at a screen

An evaluator may discard an experiment before a full measurement. Backtest that rule against past keeps before using it.
Print exactly one `EVAL_SCREENED` receipt and exit 75:

```text
EVAL_SCREENED {"version":1,"outcome":"screened","rung":2,"evidence":{"primary_upper":-42},"watches":{"eval_cost_usd":1.2}}
```

piloop stores the evidence and cost watches in a `candidate.screened` event. It records no measurement or full-panel
score. The candidate becomes a `discard`; a keep that lands during the screen stays a keep. Other exits still fail.

Honor `PILOOP_EVAL_PURPOSE`: `experiment` permits a screen; `reference` requires the full evaluator. Baseline
registration, known keeps, imported references and requested remeasurements require full results. Exit 75 during
those evaluations is an error. A manual remeasurement can therefore obtain a full score for a screened candidate.

## Metrics

Each `[[metrics]]` table in `piloop.toml` describes one metric that the evaluate command prints:

```toml
[[metrics]]
name = "accuracy"
direction = "higher"   # or "lower"
role = "primary"       # or "guardrail" or "watch"
```

- The **primary** metric is the one to improve. A campaign has exactly one, or one for each
  [track](/concepts/tracks).
- A **guardrail** must not get worse by more than its `margin`, and never past its `floor`.
- A **watch** metric is recorded and has no effect on the verdict.

[Candidates, the head and the verdict](/concepts/verdict) explains how piloop uses them.

## Per-unit results

A metric is often a sum or a mean over units: test examples, records, files. When the evaluate command reports the
result of each unit, the verdict can tell a broad gain from a gain on a few lucky units.

When piloop measures a candidate, it sets the environment variable `PILOOP_UNITS_FILE` to a file path. Write a JSON
object to that path, with one entry for each metric and each unit:

```json
{"accuracy": {"passenger-12": 0.0056, "passenger-17": 0.0, "passenger-31": 0.0056}}
```

- For each metric, the values must sum to the value on its `METRIC` line, within 0.1%. For a mean over `n` units,
  write each unit's value divided by `n`.
- Leave out metrics that are not sums, such as a latency or a wall time.
- A file that is not valid makes the evaluation fail.

piloop stores the file outside every worktree and outside the database. Agents do not see it, so that they cannot tune
their code to the result of each unit. The variable is set only for piloop's own measurements: the daemon's, and the
baseline that `piloop init` measures. It is never set when an agent runs the evaluate command.

## Evaluators

piloop records which evaluator produced each score. An **evaluator** is the evaluate command, the names and
directions of the metrics, and `link`. When you change one of these and run `piloop init`, piloop makes a new
evaluator. piloop never compares scores from two evaluators, so the daemon measures again what the next verdicts need:
the head first, then the bar of each open run and of each `ready` idea that is pinned to a candidate. Until the head has
a score, it starts only runs of ideas that are pinned to a candidate. While it holds runnable ideas, `low_water`
requests no research sweep. Then runs start from the head again.

The other keeps keep the scores of the old evaluator. The daemon measures one of them again only when you ask, for
example to compare the whole trajectory under the new evaluator:

```bash
piloop candidate remeasure 42
```

A change to a metric's role, margin or floor, or to `confidence`, does not make a new evaluator. It changes how the
next candidates are judged.

Each evaluator records its **runner** (`evaluators.runner`): how piloop runs it to measure a candidate. The only
runner is `process`: piloop runs the evaluate command as a process in a clean worktree of the candidate, as this page
describes. An **evaluation** is one run of an evaluator on a candidate, and it produces measurements.

## Shared files

- `link` in `piloop.toml` lists repo-relative paths that git ignores, such as `data` or `.venv`. piloop symlinks them
  into every worktree.
- `workspace/` is a directory that every agent of the campaign shares: notes, cached features, plots. piloop links it
  into every worktree. It is never committed.

## Where the results are

- Every commit of a run is pinned in your repo under `refs/piloop/<campaign>/r<run>/<n>`. A reference is pinned under
  `refs/piloop/<campaign>/reference/<id>`, and a keep that is rebased onto the head is pinned under
  `refs/piloop/<campaign>/rebase/<id>`. `git show`, `git diff` and `git cherry-pick` work on all of them, even after
  the worktree is gone.
- The database holds the ideas, runs, candidates, measurements, comments and events. Read it with
  `piloop sql "<statement>"`. See the [database schema](/reference/schema).
- The briefs, logs and screen transcripts of the agents are under `~/.piloop/runs/` and `~/.piloop/agent_sessions/`.
