A **campaign** is a git repo, an **evaluate command** that scores its code, and the metrics to improve. This is the
`piloop.toml` of the enwik8 example, without its limits:

```toml
name = "enwik8"
evaluate = ["uv", "run", "python", "evaluate.py"]
link = ["data", ".venv"]

[plugins.harness]
use = ["claude"]

[plugins.harness.claude]
model = "claude-opus-5-5"

[[metrics]]
name = "bytes"
direction = "lower"
role = "primary"

[[metrics]]
name = "seconds"
direction = "lower"
role = "guardrail"
margin = 60
floor = 120
repeats = 3
```

`brief.md`, next to it, tells the agents what to improve and what not to touch. `piloop init` registers the campaign
and stores a copy of `piloop.toml`, which the daemon uses: run `piloop init` again after each edit. The
[configuration reference](/reference/configuration) lists every key.

## The evaluate command

piloop runs the command at the root of a clean worktree of each commit. It appends one JSON line, its **result**, to
the pipe that `$PILOOP_RESULT_FILE` names:

```python
import json
import os

def report(result):
    line = json.dumps(result)
    if path := os.environ.get("PILOOP_RESULT_FILE"):
        with open(path, "a") as f:
            f.write(line + "\n")
    else:
        print(line)

report({"metrics": {"bytes": compressed + compressor_size, "seconds": round(cpu_seconds, 2)}})
```

piloop sets the variable only when it runs the command. Run by hand, the command prints the line:

```bash
uv run python evaluate.py
```

```text
{"metrics": {"bytes": 3688775, "seconds": 0.82}}
```

| Key | Holds |
|---|---|
| `metrics` | A number for each metric, by its name in `[[metrics]]`. Each primary and guardrail is required, a watch metric is optional. |
| `units` | Optional: the [per-unit results](#per-unit-results). |
| `evidence` | Optional: files of the worktree that explain the result, by a label, such as `{"errors": "out/errors.md"}`. piloop keeps them with the evaluation's logs, up to `[evaluation] max_evidence_mb` in `config.toml`. |

A non-zero exit, a missing or unknown metric, a value that is not a number, a second line, or a run longer than
`evaluate_timeout` seconds makes the commit a `crash`. Print the reason on stderr. Fix the seeds and the data splits,
so that the same code gets the same score. Until 0.4.0, a command that prints `METRIC <name>=<value>` lines instead
still works, and piloop posts one inbox note for its evaluator.

<Warning>
  piloop runs the evaluate command from the commit that it measures. An implementer that edits the command changes its
  own score. Tell the implementers in `brief.md` not to edit it or the data.
</Warning>

`piloop init` writes a stub `evaluate.py`. `piloop init --example <name>` makes an example campaign with a working one:

## Metrics

```toml
[[metrics]]
name = "bytes"
direction = "lower"
role = "primary"

[[metrics]]
name = "seconds"
direction = "lower"
role = "guardrail"
fraction = 0.10    # at most 10% slower than the bar for each keep
floor = 120        # and never slower than 120 s
```

| `role` | How the [verdict](/concepts/verdict) uses it |
|---|---|
| `primary` | The metric to improve. One per campaign, or one per [track](/concepts/tracks). |
| `guardrail` | May get worse than the bar by at most its tolerance for each keep, and never past `floor`. |
| `watch` | Recorded only. |

`direction` is `higher` or `lower`: which way is better. A **tolerance** is `floor`, plus one of `margin` and
`fraction`. `margin` is in the metric's units: `margin = 60` allows 60 s more. `fraction` is of the bar's value:
`fraction = 0.10` allows 10% more, whatever the bar's scale. The stops of the [ladder](#the-evaluation-ladder) take the
same keys.

### Ratio metrics

A primary or a guardrail can be a **ratio** of two metrics that the evaluate command reports. piloop computes it:

```toml
[[metrics]]
name = "solved"
direction = "higher"
role = "primary"

[[metrics]]
name = "cost_usd"
direction = "lower"

[[metrics]]
name = "cost_per_solved"
direction = "lower"
role = "guardrail"
ratio = { numerator = "cost_usd", denominator = "solved" }
fraction = 0.05
```

The evaluate command reports `solved` and `cost_usd`, with their [per-unit results](#per-unit-results), and never
`cost_per_solved`. Each side's value is the ratio of its means. The verdict resamples the units of both parts together
and takes the ratio of their sums in each resample, so the guardrail is tested with confidence:

```text
guardrails: cost_per_solved 2.4 vs 2 (+0.4; 95% worst case +0.7692 over 40 units) beyond its fraction 0.05
```

`measurements.metrics` holds the parts only. A stop of the ladder names the parts, not the ratio.

## The evaluation ladder

An evaluation ladder stops a bad candidate before the full panel. Each `[[ladder]]` table is a **rung**: a cheaper
step that the evaluate command reports before its full result, and when the climb stops there:

```toml
evaluate = ["python3", "evaluate.py"]

[[metrics]]
name = "accuracy"
direction = "higher"
role = "primary"

[[metrics]]
name = "cost"
direction = "lower"

[[ladder]]
name = "screen"
stop = { accuracy = { margin = 0.05 } }
```

The evaluate command reports the rung, then extends it into the full panel, so no question is scored twice:

```python
done = score(PANEL[:50])
report({"rung": "screen", "metrics": {"accuracy": sum(done) / len(done), "cost": 0.05}})
done += score(PANEL[50:])
report({"metrics": {"accuracy": sum(done) / len(done), "cost": 0.45}})
```

A run's commit scored 0.2 at the screen, where the baseline scored 1. piloop ended the command there:

```bash
piloop sql "SELECT candidate_id, rung, stopped, metrics FROM measurements"
```

```text
┏━━━━━━━━━━━━━━┳━━━━━━━━┳━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
┃ candidate_id ┃ rung   ┃ stopped                               ┃ metrics                         ┃
┡━━━━━━━━━━━━━━╇━━━━━━━━╇━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┩
│ 1            │ screen │                                       │ {"accuracy": 1.0, "cost": 0.05} │
│ 1            │        │                                       │ {"accuracy": 1.0, "cost": 0.45} │
│ 2            │ screen │ accuracy 0.2 vs 1 (-0.8; margin 0.05) │ {"accuracy": 0.2, "cost": 0.05} │
└──────────────┴────────┴───────────────────────────────────────┴─────────────────────────────────┘
```

The verdict of candidate#2 is `discard`: `stopped at screen: accuracy 0.2 vs 1 (-0.8; margin 0.05)`. The `ladder`
column of `piloop status` shows the same, or `reached screen` while a climb goes on. `piloop history` shows it for an
idea whose candidates have no score.

- Each rung is a measurement with its `rung`, and only a measurement without one scores. Report each line's own
  cost: piloop sums the rows.
- `stop` gives a tolerance for metrics of `[[metrics]]`, with a guardrail's keys: past `floor`, or worse than the
  [bar](/concepts/verdict#the-words) at the same rung by more than `margin` or `fraction`, the climb stops. Without
  the bar's value at the rung, only `floor` stops.
- Only a run's own commit can stop. The baseline, a head, a bar, a reference and `piloop candidate remeasure` climb
  every rung, so every bar has a value at each rung.
- At a stop, piloop sends the command SIGTERM, then SIGKILL `[evaluation] stop_grace_seconds` later, and reads no
  more lines.
- A rung with `evaluate` runs that command first, in the same worktree. It writes one line, without `rung`. Such rungs
  come first in `[[ladder]]`.
- A change to a rung's name or command, or a new rung, makes a new [evaluator](#evaluators). A change to `stop` does not.

## Per-unit results

A metric that is a sum over units, such as test examples, can report each unit. Then the verdict can tell a broad
gain from a gain on a few lucky units. Add each unit's part of each metric to the result:

```json
{"metrics": {"accuracy": 0.0112}, "units": {"accuracy": {"test-0001": 0.0056, "test-0002": 0.0, "test-0003": 0.0056}}}
```

The parts of a metric must sum to its value, within 0.1%. Leave out metrics that are not sums, such as a latency. The
agents never see the units.

## Evaluators

An **evaluator** is the evaluate command, `link`, and the names and directions of the primaries and guardrails. A
change to one of them makes a new evaluator at the next `piloop init`. piloop never compares scores of two evaluators:
it measures the head again, and runs then compare under the new one. To measure an older keep again:

```bash
piloop candidate remeasure 2
```

A change to a margin, a floor or a watch metric makes no new evaluator.

## Reopen, fork and retire

A stopped campaign can go on, start a new campaign, or end for good:

```bash
piloop campaign reopen enwik8 --reason "one more round of runs"
piloop campaign fork enwik8 --name enwik8-lzma
piloop campaign retire enwik8 --reason "tried every idea"
```

**Reopen** sets a stopped campaign active again, with its stop rule as it is. The runs, hours and tokens that the rule
limits count from the reopen, so the campaign gets each of them again. A rule that would stop it at once, a `target`
that it reached say, refuses the reopen: change the rule in `piloop.toml` and run `piloop init` instead.

**Fork** makes a new campaign that starts from the head of another one, in any state. `--at` names another version.
The fork takes its source's stored `piloop.toml`, and shares the [memory](/concepts/research-memory) of its repo. It
starts with no ideas and an empty workspace. Without `--name`, it is `enwik8-2`.

### Retire a campaign

A **retired** campaign is stopped for good, and its name is free for a new one:

```bash
piloop campaign stop enwik8
piloop campaign retire enwik8 --reason "tried every idea"
```

```text
campaign enwik8 #3 retired: its name is free
```

`retire`, like `reopen`, waits until the closing review and the runs of the stop are over. Its rows, events and archived
workspace stay, and its id still names it: `piloop status 3`. `piloop status` leaves it out unless you ask with
`--status retired`. A retired campaign never reopens: fork it.

## Files

| Path | What it is |
|---|---|
| `link` paths | Paths that git ignores, such as `data` or `.venv`, put into every worktree read-only. |
| `workspace/` | A directory that every agent of the campaign shares, for notes, caches and plots. It is never committed. An agent gets a copy when it starts, and its changes go back when it ends. |
| `refs/piloop/<campaign>/` | A git ref for each commit of each run, such as `refs/piloop/enwik8/r1/0`. `git show` works on it after its worktree is gone. |
| `~/.piloop/runs/`, `~/.piloop/agent_sessions/` | The briefs, logs and transcripts of the agents. |

The database holds the ideas, runs, candidates, measurements and comments: read it with `piloop sql`.
