Each role has a table in `piloop.toml`. By default, two implementers run at a time, for at most an hour each, in turn
on Claude Code and Codex. This campaign runs ten, for 30 minutes each:

```toml
[plugins.harness]
use = ["claude", "codex"]

[plugins.harness.claude]
model = "claude-opus-5-5"

[plugins.harness.codex]
model = "gpt-6.1-sol"

[plugins.role.implementer]
max_concurrent = 10
timeout = 1800
```

More implementers find a better best in the same hours, at more cost. Run `piloop init` after each change. The
[configuration reference](/reference/configuration#roleconfig) lists every key of a role.

Each agent is an **agent session**, with an id, a log and the tokens that it used. It signs its writes
`<role>#<id>`, such as `implementer#4`.

## The built-in roles

| Role | What it does | When it starts |
|---|---|---|
| **implementer** | Claims an idea from the board, or proposes its own, implements it, and submits versions. Its submissions are scored. | On each free slot. |
| **orchestrator** | Answers escalations and messages, and records its decisions. | Off by default: you run your own [orchestrator](/concepts/orchestrator). |

The implementer **does runs**: each run claims one idea. The orchestrator does none, and nothing that it commits is
scored.

## Define a role

A table with a new name and `runs = true` defines a role that does runs, with the implementer's defaults. This one
runs short sessions on Codex:

```toml
[plugins.role.quick]
runs = true
harnesses = ["codex"]
timeout = 300
```

Each role fills its own slots, and its agents claim from the same board. A candidate of any role can be the best. A
plugin can add a role too: see [Roles](/plugins/agents#roles).

## Sections

A **section** is one part of what `piloop status` or a brief shows, such as `## Goal` or `## Queue`.
`[plugins.section] use` lists those of `piloop status`, and a role's `sections` those of its briefs, in order. Without a
list, each shows every section that declares it. A section with parameters has a table:

```toml
[plugins.section]
use = ["headline", "trajectory", "runs"]

[plugins.section.history]
budget = 600                 # the tokens of an implementer's history
```

A brief is the role's prompt, then `brief.md`, then the role's `addendum`, then its sections. A **guide**, such as
`database`, is a section that says how to do one thing. `piloop schema <guide>` prints any guide.

## Harnesses

A **harness** is the coding agent CLI that an agent runs in. `[plugins.harness] use` lists the ones that fresh runs use
in turn. A `[plugins.harness.<name>]` table sets a harness's `model`, changes a built-in harness, or adds one:

```toml
[plugins.harness]
use = ["claude", "gateway"]

[plugins.harness.claude]
model = "claude-opus-5-5"
max_concurrent = 2   # agents of this harness at once, all roles together

[plugins.harness.gateway]
provider = "claude"
model = "claude-opus-5-5"
env = { ANTHROPIC_BASE_URL = "https://gw.example.com" }
```

A table of a new name with `provider` is that provider over its defaults. Without `provider`, it is its argv and
nothing else: see [Harnesses](/plugins/agents#harnesses). piloop refuses a harness table that no rotation names.

<Harnesses />

pi is opt-in: add `"pi"` to `use`, with a `[plugins.harness.pi]` table and its `model`. On a Claude subscription, pi
draws from extra usage, not from the plan's limits.

An agent ignores your own setup of its harness, such as your `CLAUDE.md`, skills, plugins and hooks, so it works the
same on every machine. The repo's own files and the machine's login still load. `user_config = "load"` in a harness's
table loads your setup.

## Runtimes

A **runtime** starts, steers and stops the agents' processes. `[plugins.runtime] use` sets it for the campaign, and a
role's `runtime` for one role. To run each agent in a container, see [Run agents in containers](/guides/containers).

## Watch and steer an agent

| Command | What it does |
|---|---|
| `piloop watch` | Shows the agents with their last output. |
| `piloop attach 12` | Prints the last lines that agent 12 wrote. |
| `piloop prompt 12 "<text>"` | Sends a message to the running agent. |

A run's brief, log and transcript are in `~/.piloop/runs/<run>/`, and an orchestrator's in
`~/.piloop/agent_sessions/<id>/`. When an agent ends, piloop ends every process that it started.

| `agent_sessions.state` | Meaning |
|---|---|
| `requested` | Waits for a slot. |
| `starting`, `running` | Its process starts, then works. |
| `ending` | A stop, a cancel or its run's end ends it. |
| `exited`, `killed` | It ended by itself, or piloop ended it. |
| `never_worked` | It did not start to work: its job did not start, or it ended within `startup_seconds` and left nothing. `error` says why. |

## Sessions

piloop keeps each agent's **session**, the harness's file of its prompts, tool calls and reasoning, in the
[CAS](/concepts/memory#the-cas). To read the session that made candidate 2:

```bash
piloop sql "SELECT s.id, s.session_file FROM agent_sessions s JOIN candidates c ON s.subject_kind = 'run' AND c.run_id = s.subject_id WHERE c.id = 2"
piloop cas get <session_file> > session.jsonl
```
