A program that watches or drives a campaign, such as a dashboard, a bot or a UI, reads a view at a cursor, follows the
events after that cursor, and reads the view again when an event touches it. It calls the daemon's HTTP API, or the
CLI's `--json` commands.

## The API

The daemon serves an HTTP API, `/v1`, on the Unix socket `$PILOOP_HOME/piloop.sock`, which only your user can open.
When that path is too long for a socket (104 bytes on macOS, 108 on Linux), the socket is
`/tmp/piloop-<uid>/<hash>.sock`, a hash of the home. A call there needs no token. `GET /v1/openapi.json` describes
every route:

```bash
curl --unix-socket ~/.piloop/piloop.sock 'http://piloop/v1/status?campaign=enwik8'
```

With `piloop serve --listen`, other machines call the same routes with a token of `piloop token`: see
[Run the daemon on a server](/guides/daemon#on-a-server). The `x-piloop-actor` header asks to act as an actor, such
as `orchestrator`, and writes sign as that actor. Without it, a call acts as the caller itself.

## Build a UI

This loop prints the inbox again each time a comment arrives:

```python
from piloop.actor import System
from piloop.api.client import Client
from piloop.api.contract import EventsQuery, InboxQuery, Selection
from piloop.settings import Settings

with Client.on(Settings().socket_file, System.HUMAN) as client:
    cursor = client.status(Selection(campaign='enwik8')).cursor
    while True:
        batch = client.events(EventsQuery(campaign='enwik8', after=cursor, wait=20))
        cursor = batch.next
        if any(e.subject.kind == 'comment' for e in batch.events):
            for item in client.inbox(InboxQuery(campaign='enwik8')).items:
                print(f'p{item.priority} {item.author}: {item.body}')
```

From another machine, give the client the server's URL and a token:

```python
import httpx2 as httpx

from piloop.api.client import Client

remote = Client(httpx.Client(base_url='https://piloop.example.com', headers={'Authorization': f'Bearer {token}'}))
```

Python clients use `piloop.api.client.Client` and its models. A client in another language generates its types from
the OpenAPI document. `piloop watch` is a complete UI built this way: its code is in
[`piloop/watch/`](https://github.com/hiloopai/piloop/tree/main/piloop/watch), and it imports only the API's clients
and models.

Every view answers with a `cursor`, the id of the newest event that it includes:

| Route | What it answers |
|---|---|
| `GET /v1/status` | The main facts of each campaign: its state, the best of each track, ideas, open runs, live agents, inbox count and tokens. |
| `GET /v1/overview` | The sections of each campaign's `[plugins.section] use`, as blocks of text, lines, figures and tables. |
| `GET /v1/inbox` | The inbox items that wait for you. |
| `GET /v1/inbox/{comment}` | A comment's thread. |
| `GET /v1/campaigns/{campaign}/lineage` | The campaign as a graph: see [the lineage](#the-lineage). |
| `GET /v1/agents/{agent}/output?lines=60` | An agent's last lines of output. |
| `GET /v1/comments?kind=idea&id=12` | The comments on a row. |
| `GET /v1/campaigns/{campaign}/ideas`, `GET /v1/ideas/{idea}` | The ideas, and one idea in full with its runs. |
| `GET /v1/candidates/{candidate}` | A candidate's metrics beside its parent's. |

`GET /v1/events?after=<cursor>&wait=20` holds a read until an event comes, or for `wait` seconds. Each event names
its `subject`, the row that it is about: read again only the views that the subject touches. `piloop watch` reads the
inbox again for a comment, the ideas for an idea, and the lineage for a candidate or a measurement.

A write answers with the row that it changed, at a cursor. Its effects arrive on the feed, like any other client's:

| Route | What it does |
|---|---|
| `POST /v1/inbox/ack` | Acknowledge inbox items. |
| `POST /v1/inbox/{comment}/reply` | Answer an inbox item in its thread. |
| `POST /v1/agents/{agent}/prompt` | Send a running agent a message. |
| `POST /v1/ideas/{idea}/status` | Open, drop or settle an idea, with a reason. |
| `POST /v1/ideas/{idea}/priority` | Set an idea's priority. |
| `POST /v1/candidates/{candidate}/exclude` | Take a candidate out of the race for the best, with a reason. |

A refused write answers 404 or 409 with a `ProblemDetail`: its `error` names the problem, and its `detail` says what to
do. Show the detail.

## The CLI

Three commands print the same documents, with `protocol`. Messages go to stderr. Each asks the daemon, which must run.

| Command | What it prints |
|---|---|
| `piloop status --json` | A snapshot of each campaign, and the cursor it was read at. |
| `piloop inbox --json` | The inbox items, and the cursor they were read at. |
| `piloop events --after <cursor> --json` | The events after a cursor, and the next cursor. |

## Read without a gap

1. Read a snapshot. Its `cursor` is the id of the newest event that the snapshot includes: the snapshot and the
   cursor come from one read transaction.
2. Read the events after that cursor, then after the `next` of each read. While `more` is true, read again at once.
   When it is false, add `--follow` to wait for the next event.
3. Save the cursor after you have handled a batch. After a crash or a disconnect, read again from the saved cursor.

```bash
piloop status --json
piloop events --after <cursor> --json
piloop events --after <cursor> --follow --timeout 600 --json
```

Delivery is at least once: when you resume from a saved cursor, an event that you handled before you saved it comes
again. Skip an event whose `id` you have handled. Each program keeps its own cursor. piloop keeps no state for a
reader.

`--campaign` and `--kind` filter the events. The `next` cursor still passes every event that the read examined, so a
read that matches nothing moves on. `--campaign` also keeps the events whose campaign is unknown (see
`subject.campaign` below): a campaign reader misses none of its events, and may get a few of other campaigns.

## The documents

Every document has `protocol`, the version of the documents and of the event envelope: `1`. Within a version, piloop
may add fields: ignore the fields that you do not know. A payload is not part of the protocol: the
[upgrade guide](/guides/upgrading) lists each change to one.

A read of events:

```json
{
  "protocol": 1,
  "events": [
    {
      "id": 42,
      "kind": "idea.status",
      "subject": {"kind": "idea", "id": 7, "campaign": 1},
      "actor": "orchestrator",
      "time": "2026-10-19T12:00:00.123456Z",
      "payload": {"kind": "idea.status", "old": "open", "new": "dropped"}
    }
  ],
  "next": 42,
  "more": false
}
```

| Field | Meaning |
|---|---|
| `events` | At most `--limit` events, oldest first. |
| `next` | The cursor for the next read. |
| `more` | Newer events exist already. They may not match your filters. |

`piloop status --json` has `cursor`, `daemon` (`pid`, `started`, and `listen`, the URL that other machines reach it on,
or null) and `campaigns`. Each campaign has its `id`, `name`, `path`, `parent` (`id` and `name`, or null),
`status` and `stopped_reason`, `paused` (`launches`, `all` or null) and
`paused_reason`, the current `evaluator`, the `best` of each track (its `track`, `candidate`, primary `metric`, `value`
and `delta` against the baseline; empty before the campaign has a baseline), the `new_bests` and `candidates` counts, the number of
`ideas` in each status, the `runnable` ideas, the open `runs`, the live `agents` and the unacknowledged `inbox` items.
The `tokens` fact has what its agents spent. It covers the campaigns that `piloop status` would show.

`piloop inbox --json` has `cursor` and `items`, with the filters of `piloop inbox`.

The API answers the same documents without `protocol`.

## The lineage

`GET /v1/campaigns/<campaign>/lineage` answers the campaign as a graph, for a UI that draws its history. This is a
campaign with a baseline, a new best and a worse candidate:

```bash
curl --unix-socket ~/.piloop/piloop.sock http://piloop/v1/campaigns/demo/lineage
```

|---|---|
| `cursor` | The newest event that the graph includes. Read `/v1/events?after=<cursor>&campaign=<campaign>`, and read the lineage again after an event. |
| `provider` | The instance that drew the graph: `[plugins.lineage] use`, `optimization` by default. |
| `kinds`, `statuses`, `tracks` | The graph's vocabulary. Every node's `kind` and `status`, and every key of its `scores`, names one entry. Colour a status by its `tone`: `neutral`, `accent`, `success`, `attention` or `danger`. |
| `evaluator` | What measured every score. A new one means that the scores were measured again. |
| `nodes` | Each parent before its children. A node with no `parents` is a root. A tree takes the first parent. |
| `links` | What to open from a node: a row by its `kind` and `id`, or an `agent_session` with its `harness` and `session_id`. |
| `spine` | The path from a root to the node that the campaign builds on now: the best. |
| `judged` | Who excluded the node and why, or null. |
| `series` | The nodes of the spine that moved it forward, and when: a chart of the scores over time. |

The shape is the same for every provider: [Lineage](/plugins/agents#lineage) shows how a plugin draws its own.

## The event envelope

Every event has the same fields, whatever its kind.

| Field | Meaning |
|---|---|
| `id` | The cursor. Ids grow in the order in which the events were committed: events are append-only, and a new event always takes the next id. |
| `kind` | `<subject>.<what>`, for example `idea.status`, `candidate.scored` or `comment.escalation`. |
| `subject` | The row that the event is about: its `kind` (`campaign`, `idea`, `run`, `candidate`, `measurement`, `agent_session` or `comment`), its `id` and its `campaign`. An event about the whole home, such as `limit.set`, is on `home` 1, with no campaign. |
| `actor` | Who wrote it: `daemon`, `human`, `orchestrator`, or an agent such as `implementer#12`. |
| `time` | When it was written, in UTC. |
| `payload` | The details, as stored: a JSON object with the event's `kind`. |
| `invalid` | Only when a stored value is not of its type: its stored text, under `time` or `payload`. That field is then null. |

The envelope shows each stored event as it is. It rewrites no row and invents no field. `subject.campaign` is looked up
when the event is read, so it is null when the row is gone (a deleted idea, its older events and its `idea.deleted`
included) or has no campaign (a comment on a reply to a reply).

Only piloop writes events: `piloop sql` cannot insert one. A stored value that is not strict JSON, such as `1e400`,
comes as null with its stored text under `invalid`, and the events after it read as usual.

`agent_session.identified` comes once for each harness session id of an agent, with `session_id`, `harness`,
`executable`, `role`, `model`, `campaign`, `subject` (what the agent works on, such as `run#12`, or null for an orchestrator),
`groups` (what its work belongs to, such as the run's `idea#4`) and `parent` (the agent that proposed the idea, with its
`actor`, `harness`, `executable` and `session_id`).

`agent_session.session_saved` comes for each new snapshot of an agent's session file in the CAS, with `session_file`,
its address, and `session_id`. A snapshot holds whole lines, and each starts with the bytes of the one before, so a
reader that ships lines takes only those that it has not shipped (`piloop cas get <session_file>`).

An event kind that this version of piloop does not know, such as a plugin's, comes in the same envelope with its
payload as opaque JSON. A reader that does not need it skips it and moves its cursor on.

The subjects are rows of the tables in [the data model](/reference/data-model).

## Errors

`--json` reports an error that a program can act on as a document with `error.code` and `error.message`, and exits
with status 1. The message goes to stderr too.

| Code | Meaning | What to do |
|---|---|---|
| `cursor_ahead` | The cursor is past the newest event, so it is not a cursor of this feed: it comes from another piloop home, for example. | Read a new snapshot and use its cursor. |

A cursor of another home that is behind this feed's end reads as a valid one: keep one cursor per piloop home. Other
failures, such as an unknown campaign, print a message on stderr, nothing on stdout, and exit with a status other
than 0.
