---

Run `piloop --help` for the list of commands, and `piloop <command> --help` for the options of one command.

Many commands take a `REF`: a campaign name, its id, or a path inside the campaign's repo. Without a `REF`, `piloop status`
and `piloop history` use the campaign of the current directory, else the only active campaign, else every campaign.
`piloop inbox`, `piloop inbox wait` and `piloop watch` cover every campaign.

Commands that write sign their writes with `PILOOP_ACTOR` (`human` by default). See
[Environment variables](/reference/environment).

## Set up

### piloop init

```text
piloop init [PATH] [--example enwik8|titanic-tracks|inference] [--name NAME]
```

Makes `PATH` (default `.`) a piloop campaign, starts the daemon unless one runs, registers the campaign, and waits
while the daemon measures `HEAD` as the baseline. A baseline that fails to evaluate pauses the campaign, and `init`
exits with why. Ctrl-C ends only the wait. Without a `piloop.toml`, it writes one from the template, with `brief.md`
and `evaluate.py`, and stops while `evaluate.py` is the stub. Run it again after each edit of `piloop.toml`.
`--example` creates a bundled example instead. See [Run a campaign by hand](/by-hand). `--name` registers the
campaign under `NAME` instead of the `name` of `piloop.toml`. A campaign keeps its name.

### piloop install-skills

Copies the skills of this CLI into the skill directory of every harness on your `PATH`: `~/.claude/skills` for
Claude Code (or `$CLAUDE_CONFIG_DIR/skills`), and `~/.agents/skills` for Codex, pi, Gemini CLI and Cursor. It replaces
only piloop's own skills. The installer and `piloop upgrade` run it.

### piloop doctor

Checks the install, without changing anything. Each failure says how to fix it, often with the command to run. See
[Upgrading](/guides/upgrading#check-the-install).

### piloop plugins

Lists each capability with every provider, the package and version that it comes from, and its entry point. Then it
lists what the configuration selects, and checks it as the daemon does when it starts. See
[How piloop loads plugins](/plugins/overview#how-piloop-loads-plugins).

### piloop upgrade

```text
piloop upgrade [--timeout SECONDS]
```

Upgrades the CLI, the skills and the database, and restarts a running daemon in place. `--timeout` (default 30) is
how long to wait for the daemon to come back. See [Upgrading](/guides/upgrading).

### piloop migrate

Brings the database to the schema of this CLI and prints what changed. It backs up the database first. Only this
command, `piloop serve` when it starts, and `piloop upgrade` migrate the database. Every other command refuses a
database at another schema revision and says what to run. See [Upgrading](/guides/upgrading#the-database).

## The daemon

### piloop serve

```text
piloop serve [--detach] [--check] [--listen HOST:PORT]
```

Runs the daemon in the foreground. `--detach` starts it in the background, with its output in
`$PILOOP_HOME/serve.log`. Only one daemon runs for each `PILOOP_HOME`. `--check` starts nothing: it checks what the
daemon checks when it starts, its plugins and what `config.toml` binds, and fails with the reason when it would not
start. See [How piloop loads plugins](/plugins/overview#how-piloop-loads-plugins).

`--listen` serves [the API](#the-api) and the routes of the [executor](/plugins/infrastructure#executors) to
other machines on `HOST:PORT`, in place of `[plugins.network] listen` in `config.toml`: for `workers`, the lease calls
of [`piloop worker`](#piloop-worker). Each caller sends a token of `piloop token`. An address that is not loopback needs
`tls`: see [Networks](/plugins/infrastructure#networks). Port 0 takes a free port, which `piloop restart`
keeps. `piloop status` shows the URL:

```text
daemon: pid 1754168, up 0:00:05, listening on http://127.0.0.1:35601
```

#### The API

The daemon serves an HTTP API, `/v1`, on the Unix socket `$PILOOP_HOME/piloop.sock`, which only your user can open.
When that path is too long for a socket (104 bytes on macOS, 108 on Linux), the socket is
`/tmp/piloop-<uid>/<hash>.sock`, a hash of the home. A call there needs no token. `GET /v1/openapi.json` describes
every route. With `--listen`, other machines call the same routes with a token of `piloop token` whose access reads
(`read`, `act` or `admin`). On such a machine, `PILOOP_SERVER=<url>` makes the commands that call the API, such as
`status`, `inbox`, `message` and `secret`, ask that server, with the network's credential, such as
`PILOOP_HTTPS_TOKEN`. The commands that read the database of the home, such as `history`, `attach`, `sql` and
`worker list`, then refuse: run them on the server. See [Run piloop on a server](/guides/remote-server).

```bash
curl --unix-socket ~/.piloop/piloop.sock 'http://piloop/v1/status?campaign=enwik8'
```

### piloop cas serve

```text
piloop cas serve --listen HOST:PORT
```

Serves the CAS that `[plugins.cas]` selects to [workers on other machines](/guides/workers), on `HOST:PORT`,
in a process of its own, until Ctrl-C. A worker reaches it with the `http` provider and its token of `piloop token`.
TLS is that of `[plugins.network]`: an address that is not loopback needs `tls`.

### piloop token

```text
piloop token create NAME [--access read|act|admin|worker] | list | revoke NAME
```

`create` prints a new token for the caller `NAME`. Copy it then: piloop keeps only its hash. `--access` says what its
caller may do. `worker`, the default, calls the routes of `piloop worker` and `piloop cas serve`. `read` reads, `act`
also acts on campaigns, and `admin` also changes the home. `list` shows the names, never the tokens. `revoke` deletes a token, and its next call
gets 401.

### piloop secret

```text
piloop secret set NAME [--campaign CAMPAIGN] | list | rm NAME [--campaign CAMPAIGN]
```

`set` reads a value on stdin, or asks for it on a terminal, and stores it as the secret `NAME`: the home's, or with
`--campaign` that campaign's. `list` shows the names, never the values. `rm` deletes one. See
[Secrets](/guides/secrets).

### piloop stop

```text
piloop stop [--timeout SECONDS]
```

Sends SIGTERM to the daemon and waits up to `--timeout` seconds (default 30) for it to exit. The daemon stops the
running agents. The campaigns stay active, and the next `piloop serve` continues them. See
[Stop and restart](/guides/running-for-days).

### piloop limits

```text
piloop limits
piloop limits set KEY=VALUE --reason TEXT
piloop limits unset KEY
```

Lists, sets or removes a **limit**: a value for a live key of a provider of the home, such as
`executor.pools.serve.slots.evaluation`, that wins over `config.toml` at once. The value is JSON, or
else text. `piloop status` shows each live key with its source:

```text
limit: executor.pools.serve.slots.evaluation = 1  (limit by human: the GPU is busy)
```

See [Capacity](/guides/workers#capacity).

### piloop worker

```text
piloop worker --server URL --pool NAME
```

Takes the leases of the pool `NAME` from the server at `URL`, and runs their jobs on this machine until Ctrl-C.
The [network](/plugins/infrastructure#networks) gives it its credential. It exits non-zero when the server
refuses it. See [Workers on other machines](/guides/workers).

### piloop worker list

```text
piloop worker list
```

Lists each worker: its pool, when it was last heard, its host sample, its live jobs, and why it got no lease. See
[Capacity](/guides/workers#capacity).

### piloop restart

```text
piloop restart [--timeout SECONDS]
```

Restarts the running daemon in place on the installed code. The process keeps its pid, its environment and its
service manager. The running agents continue, and the new code connects to them again. `--timeout` (default 30) is how
long to wait for the daemon to come back. It first checks, as `piloop serve --check` does, that the daemon can start
again; when it cannot, it says why and leaves the daemon running.

### piloop service-unit

Prints a systemd user unit (Linux) or a launchd agent (macOS) that keeps `piloop serve` running. It installs nothing.
See [Running for days](/guides/running-for-days#under-a-service-manager).

## Campaigns

### piloop pause

```text
piloop pause REF --reason TEXT [--evals]
```

Pauses one campaign. The daemon queues no run, requests no role and launches no requested agent, so research files no
ideas. Running work goes on, and its commits are scored. Nothing is escalated. The daemon still measures what a new evaluator or
`piloop candidate remeasure` needs, so the pause can end on a measured head. `--evals` holds those measurements too.
The pause is a state of the campaign in the database (`campaigns.paused`), not a file, so it holds wherever you run the
command. `piloop status` shows it with the reason. The paused time does not count toward `max_hours`, and no limit of
the stop rule is checked while paused.

A pause launches no agent at all, so no watchdog sweep starts for an anomaly of the running work either: the anomaly
shows in `piloop status`, and the watchdog gets it after `piloop resume`. The running agents keep their timeouts.

### piloop resume

```text
piloop resume REF
```

Ends the pause. The daemon queues runs and requests roles again at once.

### piloop campaign stop

```text
piloop campaign stop REF [--kill] [--reason TEXT]
```

Stops a campaign at once, as a [limit of the stop rule](/concepts/cost) does, also a
paused or held one. With `--kill`, the implementers are ended at once, without the prompt to save their work and stop, and their
commits are still scored. On a stopped campaign, `--kill` ends the implementers that are still winding down.
`--reason` goes into `stopped_reason`.

### piloop campaign reopen

```text
piloop campaign reopen REF --reason TEXT
```

Sets a stopped campaign active again, once its closing review and its runs are over. Its limits count from the reopen.
See [Reopen, fork and retire](/concepts/campaigns#reopen-fork-and-retire).

### piloop campaign fork

```text
piloop campaign fork REF [--at VERSION] [--name NAME]
```

Makes a new campaign that starts from `VERSION` of another one, by default its head. See
[Reopen, fork and retire](/concepts/campaigns#reopen-fork-and-retire).

### piloop campaign sync

```text
piloop campaign sync REF [--secret NAME | --token-stdin]
```

Reads a campaign's `piloop.toml` again. A campaign that the server cloned first takes its repository's new commits. See
[Update a cloned campaign](/concepts/campaigns#update-a-cloned-campaign).

### piloop campaign retire

```text
piloop campaign retire REF --reason TEXT
```

Retires a stopped campaign for good, once its closing review and its runs are over. See
[Retire a campaign](/concepts/campaigns#retire-a-campaign).

### piloop campaign parent

```text
piloop campaign parent REF PARENT_REF | --clear
```

Puts a campaign under another one of the same home, or makes it a root with `--clear`.

### piloop campaign tree

Prints every campaign under its parent, with its type and its status.

## Ideas and candidates

### piloop idea add

```text
piloop idea add REF TITLE [options]
```

Adds an idea to the board. An `open` idea runs when an implementer slot is free, in order of priority.

| Option | Meaning |
|---|---|
| `--hypothesis` | Why the idea should help, and by how much. |
| `--plan` | Concrete steps for the implementer. |
| `--from` | What prompted the idea, with ids or a URL. |
| `--priority` | 0 (urgent) to 4 (someday). Default 2. |
| `--harness` | Pin a harness instead of the rotation. |
| `--base` | The candidate id to start from, instead of the head. |
| `--track` | The track. Required when the campaign has several. |
| `--after` | An idea to wait for. Repeat it for several. |

### piloop idea status

```text
piloop idea status IDEA_ID STATUS --reason TEXT
```

Sets the status of an idea to `open` or `dropped`, with a note on the idea that says why. Only a run makes an idea
`done`. A `claimed` idea, whose run is open (queued, running or being scored), can only be dropped: `open` would queue
a second run. A dropped idea's open run finishes and is scored.

### piloop idea link

```text
piloop idea link IDEA_ID after TARGET_ID --reason TEXT
```

Links an idea that exists to another idea of the same campaign: it is held until the target is `done` or `dropped`. The link is
written in one transaction, so the daemon never takes the idea without it. An idea whose run is open takes no link,
and a link that closes a cycle is refused. The `--after` of `idea add` is checked the same way.
`piloop idea unlink IDEA_ID after TARGET_ID --reason TEXT` deletes a link, for example to a prerequisite that is
still open, to run the idea now.

### piloop idea base

```text
piloop idea base IDEA_ID CANDIDATE_ID|head --reason TEXT
```

Pins the candidate that the idea's runs start from, or clears the pin with `head`: an unpinned run starts from the
head at the time it starts. A run that is open keeps its base, and the next attempt takes the new one.

### piloop idea track

```text
piloop idea track IDEA_ID TRACK --reason TEXT
```

Moves an idea to another track of `piloop.toml`, with a note on the idea that says why. An idea whose run is open
keeps its track, because the run's commits are judged on it.

Each of these commands writes its reason in a note on the idea. The change log records the change, signed with
`PILOOP_ACTOR`, whether a command or raw SQL made it: `idea.status`, `idea.track` and `idea.base_candidate_id` with
the old and new value, and `idea.linked` and `idea.unlinked` with the target and the kind.

### piloop candidate show

```text
piloop candidate show CANDIDATE_ID
```

Prints the candidate's verdict, its metrics beside its parent's under the current evaluator, and each
[rung](/concepts/campaigns#the-evaluation-ladder) that it measured: its values, its time and why its climb stopped
there. `GET /v1/candidates/{candidate}` answers the same as data.

### piloop candidate remeasure

```text
piloop candidate remeasure CANDIDATE_ID [--repeats K]
```

Asks the daemon to measure the candidate again with the current evaluator, also on a stopped campaign. See
[Measure a candidate again](/concepts/verdict#act-on-a-candidate).

### piloop eval queue

```text
piloop eval queue
```

Lists the running evaluations, then the waiting ones in the order in which they get a slot. See
[The evaluation queue](/concepts/verdict#act-on-a-candidate).

### piloop eval cancel

```text
piloop eval cancel CANDIDATE_ID
```

Cancels the evaluation of a candidate, waiting or running, or a requested remeasure. The candidate gets a crashed
measurement that names you.

### piloop candidate import

```text
piloop candidate import REF COMMIT [--summary TEXT]
```

Registers the tree of a commit, branch or tag of the repo as a `reference` candidate: a starting point that an idea
can pin with `--base`. The daemon measures it, but never judges it. Once measured, a reference that builds on the head
can be kept by hand with `piloop candidate verdict`, and is the head then. To import a candidate
of another campaign, fetch its commit into this repo first: `git fetch <its repo> <sha>`.

### piloop candidate note

```text
piloop candidate note CANDIDATE_ID REASON [--follow-up HUNCH]... [--track TRACK]
```

Keeps a measured `discard` or `interesting` candidate in view as a starting point. Each `--follow-up` adds an open
idea pinned to the candidate. The `candidate.noted` event records the note and its author; `verdict_by` changes only with
the verdict. See [Notes](/concepts/verdict#act-on-a-candidate).

### piloop candidate verdict

```text
piloop candidate verdict CANDIDATE_ID keep|interesting|discard|crash --reason TEXT
```

Overrides the judgement of a candidate. The daemon never changes a verdict that it did not set. See
[Override a verdict](/concepts/verdict#act-on-a-candidate).

### piloop measurement add

```text
piloop measurement add CANDIDATE_ID --report FILE
```

Records a measurement that you made yourself, under the campaign's current evaluator. `FILE` is JSON:
`{"metrics": {"<name>": <value>}, "seconds": <s>, "error": "<why>"}`. Every metric of `piloop.toml` is needed unless
`error` says why the evaluation failed. The command says whether the daemon judges the candidate again. See
[Add a measurement by hand](/concepts/verdict#act-on-a-candidate).

## Status and the inbox

### piloop status

```text
piloop status [REF] [--status active|stopped|retired] [--json]
```

Prints the daemon's state, then for each campaign the sections of its `[status] sections`: by default the head, the
goal, the tracks, the trajectory, the open runs, the queue, the running agents with their last line, the recent
candidates, the incidents that agents got, the inbox and the recent events. The watchdog and research agents get the
same sections in their brief.

Without `REF`, it lists the active and stopped campaigns. `--status` lists the campaigns of that status instead, and
repeats. `--json` prints one JSON document instead: the daemon's pid and the main facts of each campaign, read at one cursor of
the [event feed](/reference/event-feed).

`status`, `inbox` (its list, `show` and `wait`) and `events` ask the daemon. Without one, they stop and say to run `piloop serve --detach`.

### piloop events

```text
piloop events [--after CURSOR] [--campaign REF] [--kind KIND]... [--limit N] [--follow] [--timeout SECONDS] [--json]
```

Prints the events after `CURSOR` (default 0, the start of the feed), oldest first, at most `--limit` (default 100,
at most 1000), then the cursor to read after next. `--campaign` keeps the events about rows of one campaign, and
`--kind` the events of a kind; repeat it for several. The next cursor passes every event that the read examined,
also those that the filters left out. `--follow` waits, up to `--timeout` seconds (default 1800), until an event
arrives. `--json` prints one JSON document. See [Event feed](/reference/event-feed).

### piloop watch

```text
piloop watch [REF] [--no-mouse]
```

Shows the campaign on one screen, with keys to act on it. `--no-mouse` leaves the mouse to the terminal, for a
multiplexer that misreads it. See [Watching a campaign](/guides/watch).

### piloop history

```text
piloop history [REF]
```

Prints the research pack: the metrics, the analysis files, the latest 60 ideas with their outcomes, the kept lineage, the findings and the digests. A research sweep reads it before it proposes ideas.

### piloop inbox

```text
piloop inbox [REF] [--kind KIND]... [--all] [--json]
```

Lists the unacknowledged items that others wrote to you, most urgent first.
`--kind` keeps only items of the given kind: `note`, `finding`, `decision`, `escalation` or `message`. Repeat it to
keep several kinds. `--all` includes acknowledged items. `--json` prints them as one JSON document, read at one cursor of the
[event feed](/reference/event-feed). See [The orchestrator and the inbox](/concepts/orchestrator).

### piloop inbox show

```text
piloop inbox show COMMENT_ID
```

Prints the thread of a comment: its root in full, then the replies with the comment that each answers, then the
comments that cite the root as `comment#<id>` or that the root cites. Every comment of a thread prints the same thread.

### piloop inbox ack

```text
piloop inbox ack IDS...
piloop inbox ack --up-to ID [--campaign REF] [--kind KIND]...
```

Marks items as seen. Only the recipients of an item acknowledge it: an item that you wrote is refused. `--up-to`
marks every unacknowledged item up to that id instead. With `--up-to`, `--campaign` keeps only the items of one
campaign, and `--kind` keeps only the items of the given kinds. With `IDS`, `--campaign` and
`--kind` are refused.
Nothing waits on an acknowledgement. To revise a decision, write a `decision` comment on its target.

### piloop inbox choose

```text
piloop inbox choose ID CHOICE
```

Answers an escalation with one of its choices: a `decision` reply in its thread, signed as you, and an
acknowledgement. `piloop inbox show ID` lists the choices. See [Escalations](/concepts/orchestrator#escalations).

### piloop inbox reply

```text
piloop inbox reply ID BODY [--priority N]
```

Answers an item with a `decision` on the root of its thread, `in_reply_to` the item. The answer is an inbox item
itself, so it ends `piloop inbox wait` for every orchestrator but you.

### piloop inbox wait

```text
piloop inbox wait [REF] [--after EVENT_ID] [--timeout SECONDS]
```

Blocks until something needs the orchestrator, then prints it, one line each, and the command for the next wait. It
returns for a new inbox item that someone else wrote, a campaign that the daemon stopped,
an anomaly that the daemon gave to a watchdog, and the daemon's verdict on a measured candidate. `--after` is the cursor
that the last wait printed (default: now). `--timeout` (default 1800) is how long to wait before it returns with
nothing. Set the timeout of your shell tool above it.

### piloop escalate

```text
piloop escalate TARGET [--priority N] < form.json
piloop escalate TARGET --guide
```

Files an escalation on `TARGET` (`idea#12`), with its form as JSON on stdin. The campaign's `[plugins.escalation]`
provider checks the form, and a refusal says what to fix. `--guide` prints the provider's fields, limits and an example.
`--priority` defaults to 2.

### piloop message

```text
piloop message REF BODY [--priority N]
```

Writes to the campaign's orchestrator, which answers in your inbox. `--priority` defaults to 2. See
[Messages](/concepts/orchestrator#the-inbox).

### piloop wake

```text
piloop wake [REF] [--budget TOKENS]
```

Prints what the orchestrator of a campaign needs first, in a fixed budget of tokens (default 2000). Without `REF`, it
uses the campaign of the current directory, else the only active campaign, else the whole home. See
[Memory](/concepts/memory).

### piloop journal

```text
piloop journal LINE [--campaign REF]
```

Adds one line, at most 280 bytes, to the campaign's append-only journal: a decision, a plan or a result, with its
ids. Without `--campaign`, it uses the campaign of the current directory, else the only active campaign.

## Agents

### piloop launch

```text
piloop launch REF ROLE [--harness NAME] [--model MODEL] [--reason TEXT]
```

Asks the daemon for one more agent of `ROLE`, a sweeping role: `watchdog`, `research` or a
[role that you defined](/concepts/roles#define-a-role). The daemon starts it at once, within the role's
`max_concurrent`.
Only the daemon starts implementers, because an implementer needs a run.

### piloop attach

```text
piloop attach AGENT_SESSION_ID
```

Prints the last 40 lines that an agent wrote, running or ended, on any machine. A running agent's lines come from the
latest snapshot of its session, a few seconds old and at most 30. An agent has no terminal to type into: use `piloop prompt` to
send it a message.

### piloop prompt

```text
piloop prompt AGENT_SESSION_ID TEXT
```

Queues `TEXT` for the next turn of a running agent of any role, as a `note` on the agent. The daemon gives it to the
agent's runtime, and the command waits up to 20 seconds to say whether it is queued:

```text
queued comment#31 for agent_session#4: it reads it at its next turn
```

An agent reads a message only between two tool calls. `comment.delivered` on the agent records the read, and
`comment.undelivered` an agent that ended first.

When the [runtime](/concepts/roles#runtimes) of the agent cannot take it, the command says why. The agent session ids are in
`piloop status`.

### piloop run cancel

```text
piloop run cancel RUN_ID [--wrap-up]
```

Cancels a queued or running run at once. A queued run never starts, and a run whose implementer fails to
start is not launched again. A running implementer is ended with
[every process that it started](/concepts/roles#watch-and-steer-an-agent), also those in sessions of their own. With `--wrap-up`, the implementer is first told to
save its work and stop, and ended 10 minutes later. The run closes as `cancelled`, unless its implementer left its finding
before the daemon ended it: a later finding is refused. Its commits are scored, it counts toward no run limit, and its idea is dropped: set the idea `open` to run it again.

### piloop run extend

```text
piloop run extend RUN_ID --by <duration>
```

Gives the running implementer of a run more time, such as `--by 1h` or `--by 90m`. Extensions add up:

```text
run#12: agent_session#40 may run 1:00:00 past its timeout
```

Its timeout ends it that much later, also on a worker elsewhere. A note on the implementer tells it its new deadline.
A run that has no running implementer is refused.

### piloop agent cancel

```text
piloop agent cancel AGENT_SESSION_ID [--wrap-up]
```

Cancels an agent of any role at once: a sweep, or an implementer, whose run it cancels as
`piloop run cancel` does. A requested agent never starts. A running one is ended with every process that it started,
at once or, with `--wrap-up`, after it was told to save its work and stop.

### piloop agent messages

```text
piloop agent messages [--harness <harness>]
```

Takes the messages that wait for the agent of this shell, and prints them, one per line by default. A hook of the
harness runs it during a turn, with `--harness` for the format that the hook reads: the `claude` harness passes
`--harness claude`.

## The database

### piloop sql

```text
piloop sql STATEMENT|-
```

Runs one SQL statement against the piloop database. Schema changes, transactions, `ATTACH` and all but the read-only
`PRAGMA`s are denied. So are writes to piloop's internal tables and to the full-text indexes. Everything else,
including `DELETE`, is allowed. The output stops at 500 rows. See the [database schema](/reference/schema).

With `-`, the statement is read from stdin, so a text with backticks, `$(…)` or `$VAR` reaches the database unchanged.
Pipe it in from a quoted heredoc, which the shell does not expand:

```bash
piloop sql - <<'EOF'
INSERT INTO comments (target_kind, target_id, author, kind, body)
VALUES ('idea', 12, 'human', 'note', 'Run `make bench` first: it''s the slow step.');
EOF
```

### piloop schema

```text
piloop schema [GUIDE ...]
```

Prints every guide to the database, then every table. With names, it prints only those guides, such as
`piloop schema provenance`. The orchestrator reads it before it writes. A brief has the guides of its agent's role, and
names the others.

## The workspace archive

### piloop restore

```text
piloop restore REF [SUBJECT | PATH]
```

Writes archived workspace files back into the campaign's workspace: the files of `SUBJECT` (`idea#12`, or `12` for an idea), one
workspace-relative `PATH` or everything under it, or with neither, every archived file. See
[Getting files back](/concepts/archive).

### piloop store status

Prints the CAS provider and, for a cache, what it holds (blobs, their local size, how many are on the remote), how much of each campaign was
archived, and how many settled subjects and stopped campaigns are still due:

```text
to archive: 0 settled subject(s), 0 stopped campaign(s) (the daemon works through them in the background, one at a time)
```

### piloop store evict

Uploads the blobs that the remote does not have yet, then drops local copies as `[plugins.cas]` says. The daemon does this
every hour.

### piloop store verify

```text
piloop store verify [REF]
```

Checks that the store holds every blob of every archive: local copies are hashed again, evicted ones are looked up on
the remote. Exits non-zero when one is missing or corrupt.

### piloop cas get

```text
piloop cas get CID
```

Prints the file `CID` of the CAS to stdout: a blob as it was put, or a chunked file such as an agent's session file
(`agent_sessions.session_file`) whole. Exits non-zero when the CAS does not have it.
