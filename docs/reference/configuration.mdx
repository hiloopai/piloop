`piloop.toml` is at the root of the campaign repo. `piloop init` reads it again each time you run it, and stores a
copy. The daemon uses that copy, so an edit takes effect only when you run `piloop init`.

The home's `config.toml` can give every campaign of the home its `[plugins]` tables. A campaign's `piloop.toml`
overrides them key by key:

```toml
# config.toml
[plugins.fact_source]
use = ["campaign", "optimization", "leases", "models", "spend"]

[plugins.stop_rule]
max_hours = 24
```

```toml
# piloop.toml
[plugins.stop_rule]
max_hours = 48   # this campaign only; the home's use still applies
```

A key takes the first value that it finds, in this order: `PILOOP_CAMPAIGN_<KEY>`, `piloop.toml`, the home's
`config.toml`, then piloop's default. A table merges key by key, and any other value, such as a list, replaces. A table
of `config.toml` that a campaign does not use is no error.

To override a key when `piloop init` reads the file, set `PILOOP_CAMPAIGN_<KEY>`. Join nested keys with `__`, for
example `PILOOP_CAMPAIGN_PLUGINS__RUNTIME__USE=subprocess` or `PILOOP_CAMPAIGN_PLUGINS__ROLE__IMPLEMENTER__MAX_CONCURRENT=2`. The stored copy keeps the
override until the next `piloop init`. The variable has no effect on `piloop serve`.

A type in the tables links to the section that describes it. A table that you leave out has the defaults of its
section.

## Tolerance

How far a metric may go: never past `floor`, nor worse by more than `margin` or `fraction`.

A guardrail has one, and its regression is from the baseline's value. Each stop of a rung of the ladder has one
too, and its regression is from the best's value at that rung.

| Key | Type | Default | Description |
|---|---|---|---|
| `floor` | number \| null | `null` | Optional. The worst value allowed: at least this for `higher`, at most this for `lower`. |
| `margin` | number \| null | `null` | The largest regression, in the metric's own units: `20` for 20 ms. Not with `fraction`. |
| `fraction` | number \| null | `null` | The largest regression, as a fraction of the value it is from: `0.1` for 10%. Not with `margin`. |

## Metric

One metric that the evaluate command reports, by its name in `metrics` of its result.

Its `floor`, `margin` and `fraction` (`Tolerance`) apply to a guardrail, which needs a `margin` or a
`fraction`, and to each primary of a campaign with several tracks: for a candidate of another track, that
primary is a guardrail.

| Key | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | The name of the metric, as the evaluate command reports it. |
| `direction` | `higher` \| `lower` | required | `higher` when a larger value is better, `lower` when a smaller value is better. |
| `role` | `primary` \| `guardrail` \| `watch` | `"watch"` | How the metric decides. The `primary` metric of a track ranks its candidates, and each track has exactly one. With the default best rule, a candidate may be best only when each `guardrail` is worse than the baseline's by at most its `margin` or `fraction`, and never past its `floor`. A `watch` metric is recorded and never decides. |
| `track` | string \| null | `null` | Primary metrics only. The name of the track (objective) that this metric is the primary of. | `ratio` | [Ratio](#ratio) \| null | `null` | Optional. Primaries and guardrails only. piloop computes this metric from two others of `[[metrics]]`, and the evaluate command does not report it. Example: `{ numerator = "cost_usd", denominator = "solved" }`. |

## Harness

`[plugins.harness.<name>]`: how to launch one coding agent, with which model, and how many at once.

piloop substitutes these placeholders in the argument lists: `{model}`, `{effort}` (the role's `effort`),
`{session_id}`, `{cwd}` (the agent's working directory), `{log_dir}` (the directory of the agent's brief and
logs) and `{prompt}` (the first prompt, which names the file that holds the brief). An element that is exactly
`{mcp}` expands to the role's MCP servers, in the harness's own flags. The built-in harnesses run without
permission prompts: agents run in worktrees that the daemon owns and throws away, and a sandbox that cannot reach
the repo's `.git` cannot commit.

When `headless` contains `{session_id}`, piloop creates the session id. Otherwise the runtime reads it with
`session_id_pattern`. When the agent ends, the harness finds its session file by this id and reads the tokens
the agent spent. Without either, no tokens are recorded.

|---|---|---|---|
| `model` | string \| null | `null` | The model id, which fills `{model}` in the argv, for example `claude-opus-5-5`. A role overrides it (`[plugins.role.<name>] model`). A harness in a rotation needs one of the two. |
| `max_concurrent` | integer \| null | `null` | The maximum number of agents of this harness, across all roles of the campaign, that are started or queued to start. Example: 2 when the provider of its model limits the request rate. When it is the turn of a harness at its limit, the slot goes to the next harness of the rotation. An idea or request that pins this harness waits. When unset, only the limits of the roles apply. |
| `executable` | string | required | The program to run. |
| `headless` | list\[string\] | required | The arguments for a run without a terminal. Must include `{prompt}`. |
| `resume` | list\[string\] | `[]` | The arguments that continue the session of a run with a new prompt. ## ImplementerRole

`[plugins.role.implementer]`, and every `[plugins.role.<name>]` table with `runs = true`: a role that does runs.

The run queue starts its agents. Each agent claims one idea, in a new checkout of the best (or of another
candidate, `--base`), and its versions are scored into the pool. A new role of this kind takes the implementer's defaults, its prompt included.

| Key | Type | Default | Description |
|---|---|---|---|
| `timeout` | number | `3600` | The number of seconds one implementer may run before it is stopped. Its brief states it. A quarter of it before, at most `wrap_up_lead`, the daemon tells the implementer to wrap up. |
| `max_concurrent` | integer | `2` | The maximum number of implementers that run at the same time, on all workers together. A run that is being scored after its implementer ended does not count. More of them find a better best in the same hours, at more cost. |
| `runs` | boolean | `true` | The agents of this role do runs. A table of a new name needs `runs = true`. |
| `wrap_up_lead` | duration | `"PT10M"` | How long before its `timeout` the daemon tells an implementer to wrap up, at most a quarter of the timeout. |
| `end_grace` | duration | `"PT1M"` | How long after an implementer ended its run (`piloop run end`) the daemon ends it, and every process that it left: its last tool call returns first. |
| `startup_relaunches` | integer | `2` | How many times a run is queued again with a new implementer after its implementer failed to start. Then the run fails. A failure at startup is a fault of the host or the harness, not an attempt at an idea. A run that its campaign would not launch now (paused, stopped, within its wrap-up lead, or held by the startup breaker) is not queued again: it fails at once and frees its slot. |

| Key | Type | Default | Description |
|---|---|---|---|
| `image` | string | required | The image of the agents' containers. It has the harness CLIs that the campaigns use and git. A glibc-based image: piloop's own CLI runs in it from the worker's install. |
| `allow` | list\[string\] | `["api.anthropic.com", "api.openai.com"]` | What agents may reach: `host`, `host:port` or `*.domain` (port 443 when none). The HTTP MCP servers of an agent's role are added to it. A model gateway on this machine is `127.0.0.1:<port>`. |
| `network` | string | `"piloop"` | The Docker network of the containers, which piloop creates as `--internal`: it has no route out. |
| `proxy_port` | integer | `3129` | The port of the egress proxy on the network's gateway. A fixed one, so that an agent survives a restart of its worker: the next worker serves it on the same address. |
| `executable` | string | `"docker"` | The Docker CLI, or a CLI that takes the same arguments, such as `podman`. |
| `link_depth` | integer | `2` | How many folder levels of a worktree piloop reads for the links of `link`, such as `data/train.csv`. |
| `docker_seconds` | number | `600` | How long a call of the Docker CLI that sets up or removes a container may take, a pull of the image included. |

With `provider = "subprocess"`, the table has no other key.

#### `[plugins.secrets]`

The secrets provider. Without a table: `local`.

With `provider = "local"`, the table has no other key.

## Deprecated keys

These keys still work. Each one shows a `PiloopDeprecationWarning` that names the file, the key, its replacement and the release that removes it. The changelog lists them too.

- `scoring` of `[evaluator]` is removed: piloop scores what an implementer submits. piloop drops the key. 0.5's `run_end` scoring is gone: every version of a run that its implementer does not submit is `skipped`.
- `[plugins.memory]` and the `lessons` section are removed with research memory. piloop drops them. The lessons, documents and journal are gone: an orchestrator keeps its notes as `note` comments on the campaign. A section table of `provider = "lessons"` goes too, and so does its name in `[plugins.section] use` and in a role's `sections`.
- `wake_budget` of `[agents]` is removed with `piloop wake`. piloop drops it.
