The database is the contract between every actor: you, the orchestrator, the daemon and the agents. They read and
write the same tables, with `piloop sql` or through the CLI. CHECK constraints fix the allowed values, and triggers
record who changed a row and log each change in `events`.

- A **campaign** is one repo. An **agent session** is one agent process, in any role.
- A **comment** or an **event** points at any row through `(target_kind, target_id)`, so it has no foreign key.
- An **idea** is something to try. `idea_links` holds an `after` link between two ideas of one campaign.
- A **run** is one implementer session, from its base: the best, or the candidate of `--base`. `run_claims` holds the
  ideas that it claimed, any number. `submissions` holds what it submitted for each claim, and a candidate's `idea_id`
  the claim that it was made for, or last submitted for.
- A **candidate** is a distinct state of the code, identified by its git tree. `parent_id` is its line.
- An **evaluator** is one version of the evaluate command and the metrics. A **measurement** is one run of an
  evaluator on a candidate.

`campaigns.evaluator_id` and `runs.base_candidate_id` have no foreign key: it would make a cycle. Each line of the
diagram is a foreign key, labeled with its column. The [database schema](/reference/schema) has the full DDL, by the
plugin that owns each table.

## Team tables

The agents of a campaign can make tables of their own, for what piloop's tables do not hold: who works with whom,
what is done, verdicts on parts of the task. They live in the schema `team` of `piloop sql`: one SQLite file per
campaign, `$PILOOP_HOME/projects/<campaign id>/team.db`. An agent reaches only its own campaign's. You reach the
one that `--campaign` names, else the only campaign that is not retired, else the one of the current directory.

```sql
CREATE TABLE team.verdicts (idea_id INTEGER NOT NULL, verdict TEXT NOT NULL, by TEXT NOT NULL DEFAULT (actor()));
INSERT INTO team.verdicts (idea_id, verdict) VALUES (12, 'hard: needs a new lemma');
SELECT i.id, i.title, v.verdict, v.by FROM ideas i JOIN team.verdicts v ON v.idea_id = i.id;
```

- `CREATE` and `DROP` of a `TABLE`, an `INDEX` or a `VIEW`, and `ALTER TABLE`, work in `team` only. A trigger or a
  virtual table does not.
- `actor()` returns whom the statement signs as, such as `implementer#12`. Nothing makes a table use it.
- A view in `team` reads only `team`. To combine them with piloop's tables, JOIN them in the query.
- A write to `team` never waits for the daemon's writes, and the daemon never reads these tables.
- Each statement runs for at most 5 s, and the file grows to at most 256 MiB (`[sql]` in
  [`config.toml`](/reference/configuration)). These limits apply to every caller of `piloop sql`.
- A fork starts with no team tables. Retiring the campaign archives the file with the campaign's other files.


The daemon and the CLI move a row from one value to the next, as [ideas and runs](/concepts/ideas-and-runs),
[the pool](/concepts/pool) and [agents](/concepts/roles#watch-and-steer-an-agent) show. `piloop sql` can set any value.
