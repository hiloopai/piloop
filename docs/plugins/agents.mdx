A harness is the coding agent CLI that an agent runs in, and an MCP server gives it tools. A runtime starts and steers the agents. A role says what an agent does, and its triggers say when it starts. A section
is one part of what `piloop status`, a brief or a UI shows. [Agents and roles](/concepts/roles) describes them as a
user sees them.

## Harnesses

A harness provider holds what piloop knows about one coding agent CLI. This one is Claude Code's beta build, which every
campaign that does not set `harnesses` rotates through:

```python
from typing import ClassVar

from piloop.capabilities import Claude


class ClaudeBeta(Claude):
    """``claude_beta``: Claude Code installed as ``claude-beta``."""

    DEFAULT: ClassVar[bool] = True
    executable: str = 'claude-beta'
```

```toml
[project.entry-points."piloop.harnesses"]
claude_beta = "my_package:ClaudeBeta"
```

### The contract

A harness provider is a subclass of `Harness`. Its fields are the keys of `[plugins.harness.<name>]` with its defaults. Its
methods hold what piloop knows about the CLI: `mcp` writes a role's MCP servers in its flags, `usage` reads the tokens
from its session files when an agent ends, `messages` is what its hook prints for a message, and `skills_dir` is where
it reads user skills.

<ContractHarness />

A table with a new name and `provider = "<harness>"` is that harness over its defaults. A table with a new name and no
`provider` runs its argv and does nothing else: it takes no MCP servers, and records no tokens.
[Harnesses](/concepts/roles#harnesses) lists the built-in ones.

## MCP servers

A package can ship an MCP server, so that a campaign names it without its command. The harnesses know two transports,
so the server subclasses one of them, `HttpServer` or `StdioServer`, and gives its keys their defaults:

```python
from piloop.capabilities import StdioServer


class XSearch(StdioServer):
    """``x_search``: an X search, from this package."""

    command: list[str] = ['x-search-mcp', '--max-usd', '1']
    env: list[str] = ['XAI_API_KEY']
```

```toml
[project.entry-points."piloop.mcp_servers"]
x_search = "my_package:XSearch"
```

A campaign then lists `"x_search"` in a role's `mcp`: a provider that needs no keys is an instance of its own name.

## Runtimes

piloop starts each agent through a runtime. The runtime starts the agent's process. piloop then waits for the agent,
sends it messages and stops it through the runtime.

### Example: run the agents under `nice`

This runtime starts each agent as the built-in runtime `subprocess` does, but with a lower CPU priority:

<ExampleNiceRuntime />

Install it, then select it in `piloop.toml` and run `piloop init .`:

```toml
[plugins.runtime]
use = "nice"
```

A role can select its own: `[plugins.role.research] runtime = "nice"`. `[plugins.runtime.nice]` in `config.toml` holds
the runtime's settings.

### The contract

A runtime is a pydantic model, a subclass of `RuntimeConfig`: the name of its entry point is its name, and its fields
are the keys of `[plugins.runtime.<name>]`. Its `open(name)`, with the name of the instance, returns an object with the methods of the `Runtime` protocol. That
object starts the `headless` argv of a harness, with the first prompt in it. [Runtimes](/concepts/roles#runtimes)
says what a runtime does for you.

## Roles

[Agents and roles](/concepts/roles#define-a-role) defines a role in `piloop.toml`. A plugin can ship one too.

### Example: a role and a trigger from a plugin

This plugin adds a trigger, `no_keep`, that starts an agent when no candidate
was kept for some hours. It also adds a role, `auditor`, that uses this trigger:

```python
from datetime import datetime, timedelta
from importlib.resources import files

from sqlalchemy import func, select

from piloop.capabilities import Fire, Outcome, Pass, SweepRole, Trigger, TriggerName
from piloop.db.models import Candidate


class NoKeep(Trigger):
    """``no_keep``: no new keep for ``hours`` hours, once per agent of the role."""

    hours: float = 6

    def fire(self, p: Pass) -> Fire | None:
        return Fire(f'no keep for {self.hours:g} hours') if p.now >= self._due(p) else None

    def due_in(self, p: Pass) -> timedelta | None:
        return max(self._due(p) - p.now, timedelta(0))

    def _due(self, p: Pass) -> datetime:
        keeps = select(func.max(Candidate.created_at)).where(
            Candidate.campaign_id == p.campaign.id, Candidate.verdict == Outcome.KEEP
        )
        latest = p.s.scalar(keeps) or p.campaign.created_at
        started = p.last.started_at if p.last is not None else latest
        return max(latest, started) + timedelta(hours=self.hours)


class Auditor(SweepRole):
    """``auditor``: the role's defaults are its fields' defaults."""

    PROMPT = files(__package__) / 'auditor.md'  # ships in the package
    triggers: list[TriggerName] = ["no_keep"]
    timeout: float = 1800
```

```toml
[project.entry-points."piloop.triggers"]
no_keep = "my_package:NoKeep"

[project.entry-points."piloop.roles"]
auditor = "my_package:Auditor"
```

Any campaign can then name `no_keep` in the triggers of a role, with `[plugins.trigger.no_keep] hours = 12` to change
its parameter, and gets the `auditor` role, with its table in `piloop.toml` over the package's defaults, at its next
`piloop init`.

### The contract

A role is a table in `piloop.toml`: its prompt, when it starts (the run queue, or its triggers), where it works, how
(harnesses, models, MCP servers, timeout, concurrency) and what it may file. A role that does runs (`runs = true`)
takes ideas from the run queue, and its commits are scored and judged. A sweeping role starts on its triggers, and
nothing it commits is scored. A plugin's role is a subclass of `SweepRole` or of `ImplementerRole` whose fields have
the role's defaults, and whose `PROMPT` is the prompt that starts its brief: a file of its package. `prompt` in the
table overrides it. [Roles](/concepts/roles) describes each key.

## Triggers

A `sql` trigger needs no code: its query fires the role when it returns a row, as in
[Define a role](/concepts/roles#define-a-role). A trigger with code of its own comes from a plugin, as `no_keep` above.

### The contract

A trigger is an instance that a role names in `[plugins.role.<name>] triggers`, with its parameters in
`[plugins.trigger.<name>]`. A plugin's trigger is a subclass of `Trigger`: its fields are its parameters. On each pass, for each sweeping role
without a pending request, the daemon calls `fire(p)` of each trigger of the role in order. A pass comes when
something changes in the campaign, or in what a trigger names in `WAKES_ON`, and when the time that a trigger's
`due_in` returns comes. A trigger that compares a time returns when the comparison turns: there is no pass on a timer.
The rows that it reads are the models of `piloop.db.models`, the [data model](/reference/data-model).

## Sections

### Example: the keeps per hour

```python
from sqlalchemy import func, select

from piloop.capabilities import Figure, Figures, Rendered, Rendering, Section, Surface
from piloop.db.models import Candidate


class KeepRate(Section):
    """The keeps per hour since the campaign started."""

    SHOWN_IN = frozenset({Surface.STATUS})
    ORDER = 175  # after the evaluations

    def render(self, r: Rendering) -> Rendered | None:
        mine = (Candidate.campaign_id == r.campaign.id) & (Candidate.verdict == 'keep')
        kept = r.s.scalar(select(func.count()).select_from(Candidate).where(mine)) or 0
        hours = (r.now - r.campaign.created_at).total_seconds() / 3600
        if not kept or hours <= 0:
            return None
        rate = Figure(label='keeps per hour', value=round(kept / hours, 2))
        return Rendered(title='Keep rate', blocks=(Figures(figures=(rate,)),))
```

Declare it with an entry point in `piloop.sections`. `piloop status` then shows it after the evaluations, wherever
`[plugins.section] use` is not set.

### The contract

A section is an instance that a list of sections names, with its parameters in `[plugins.section.<name>]`. A plugin's
section is
a subclass of `Section`: its fields are its parameters. Its `render` returns a `Rendered`, a title and its blocks. A
block is one of four kinds: `Text`, `Lines`, `Figures` (named values, a number with its unit) and `Table`.
`piloop status`, a brief, the API and a UI render each kind their own way, so a section never formats for one reader.
