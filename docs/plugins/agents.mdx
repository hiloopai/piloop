A harness is the coding agent CLI that an agent runs in, and an MCP server gives it tools. A runtime starts and steers
the agents. A role says what an agent does and when it starts. A section is one part of what `piloop status`, a brief
or a UI shows. A lineage is the graph of a campaign that a UI draws. [Agents and roles](/concepts/roles) describes
them as a user sees them.

## Harnesses

A harness provider holds what piloop knows about one coding agent CLI. This one is Claude Code's beta build, which every
campaign that does not set `[plugins.harness] use` rotates through:

```python
from typing import ClassVar

from piloop.capabilities import Claude


class ClaudeBeta(Claude):
    """``claude_beta``: Claude Code installed as ``claude-beta``."""

    DEFAULT: ClassVar[bool] = True
    executable: str = 'claude-beta'
```

```toml
[project.entry-points."piloop.harnesses"]
claude_beta = "my_package:ClaudeBeta"
```

### The contract

A harness provider is a subclass of `Harness`. Its fields are the keys of `[plugins.harness.<name>]` with its defaults. Its
methods hold what piloop knows about the CLI: `mcp` writes a role's MCP servers in its flags, `usage` reads the tokens
from its session files when an agent ends, `messages` shows the messages that wait for an agent, and `skills_dir` is
where it reads user skills.

[Harnesses](/concepts/roles#harnesses) lists the built-in ones, and how a table with a new name uses them.

## MCP servers

A package can ship an MCP server, so that a campaign names it without its command. The server subclasses
`HttpServer` or `StdioServer`, and gives its keys their defaults:

```python
from piloop.capabilities import StdioServer


class XSearch(StdioServer):
    """``x_search``: an X search, from this package."""

    command: list[str] = ['x-search-mcp', '--max-usd', '1']
    env: list[str] = ['XAI_API_KEY']
```

```toml
[project.entry-points."piloop.mcp_servers"]
x_search = "my_package:XSearch"
```

A campaign then lists `"x_search"` in a role's `mcp`: a provider that needs no keys is an instance of its own name.

## Runtimes

piloop starts each agent through a runtime. The runtime starts the agent's process. piloop then waits for the agent,
sends it messages and stops it through the runtime.

### Example: run the agents under `nice`

This runtime starts each agent as the built-in runtime `subprocess` does, but with a lower CPU priority:

<ExampleNiceRuntime />

Install it, then select it in `piloop.toml` and run `piloop init .`:

```toml
[plugins.runtime]
use = "nice"
```

A role can select its own: `[plugins.role.<name>] runtime = "nice"`. `[plugins.runtime.nice]` in `config.toml` holds
the runtime's settings. [Runtimes](/concepts/roles#runtimes) lists the built-in ones.

### The contract

A runtime is a pydantic model, a subclass of `RuntimeConfig`: the name of its entry point is its name, and its fields
are the keys of `[plugins.runtime.<name>]`. Its `open(name)`, with the name of the instance, returns an object with
the methods of the `Runtime` protocol. That object starts the `headless` argv of a harness, with the first prompt in
it.

## Roles

[Agents and roles](/concepts/roles#define-a-role) defines a role that does runs in `piloop.toml`. A package can ship
a role too, in two kinds.

### Example: a role that does runs

This plugin adds `quick`, a role that does runs with short sessions:

```python
from piloop.capabilities import ImplementerRole


class Quick(ImplementerRole):
    """``quick``: the role's defaults are its fields' defaults."""

    timeout: float = 300
    max_concurrent: int = 2
```

```toml
[project.entry-points."piloop.roles"]
quick = "my_package:Quick"
```

Any campaign then gets the `quick` role, with its table in `piloop.toml` over the package's defaults, at its next
`piloop init`.

### The contract

A role is a table in `piloop.toml`: its prompt, where it works, how (harnesses, models, MCP servers, timeout,
concurrency) and what it may write. A role's entry point names a subclass of one of two classes:

| Class | Its agents | When they start |
|---|---|---|
| `ImplementerRole` | Do runs: each claims an idea from the board, and its commits are scored into the pool. | One run per free slot. |
| `StartsItsAgents` | Do no runs: nothing that they commit is scored. | When the provider asks, and on `piloop launch`. |

The fields of the subclass are the role's defaults, and its `PROMPT`, a file of its package, starts its brief. `prompt`
in the table overrides it.

A `StartsItsAgents` role decides when its agents start, such as on a timer or on an event. On each pass over a
campaign, the daemon calls its `request`, which inserts the rows of the agents it wants and says when to ask again.
`wakes_on` names the events that make the daemon pass for the role, and `wakes_while` says whether it wakes while the
campaign is paused, held or stopped. The daemon launches each row within the role's `max_concurrent` and the free
slots, and calls `launch` in a thread of its own. piloop has no built-in role of this kind.

A package's role keeps its whole table and its keys, also a name or a key that piloop's own roles no longer have, such
as `watchdog` or `interval`.

## Sections

### Example: the new bests per hour

```python
from piloop.capabilities import Figure, Figures, Rendered, Rendering, Section, Surface
from piloop.plugins.campaign_type.kit.pool.scored import new_bests


class BestRate(Section):
    """The new bests per hour since the campaign started."""

    SHOWN_IN = frozenset({Surface.STATUS})
    ORDER = 175  # after the evaluations

    def render(self, r: Rendering) -> Rendered | None:
        found = len(new_bests(r.s, r.campaign))
        hours = (r.now - r.campaign.created_at).total_seconds() / 3600
        if not found or hours <= 0:
            return None
        rate = Figure(label='new bests per hour', value=round(found / hours, 2))
        return Rendered(title='New bests', blocks=(Figures(figures=(rate,)),))
```

Declare it with an entry point in `piloop.sections`. `piloop status` then shows it after the evaluations, unless
`[plugins.section] use` is set.

### The contract

A section is an instance that a list of sections names, with its parameters in `[plugins.section.<name>]`. A plugin's
section is a subclass of `Section`: its fields are its parameters. Its `render` returns a `Rendered`, a title and its blocks. A
block is one of four kinds: `Text`, `Lines`, `Figures` (named values, a number with its unit) and `Table`.
`piloop status`, a brief, the API and a UI render each kind their own way, so a section never formats for one reader.
[Sections](/concepts/roles#sections) lists the built-in ones.

## Lineage

A **lineage** is a campaign as a graph that a UI draws without knowing the campaign's type. Its provider makes the
graph that `GET /v1/campaigns/{campaign}/lineage` answers ([the event feed](/reference/event-feed#the-lineage) shows
one). This provider calls the built-in `optimization` and keeps only the spine:

```python
from sqlalchemy.orm import Session

from piloop.capabilities import Graph, OptimizationLineage
from piloop.db.models import Campaign


class SpineOnly(OptimizationLineage):
    """``spine_only``: ``optimization``, with only the nodes of the spine, for a small screen."""

    def graph(self, s: Session, campaign: Campaign) -> Graph:
        full = super().graph(s, campaign)
        spine = set(full.spine)
        return Graph(**(dict(full) | {'nodes': [n for n in full.nodes if n.id in spine]}))
```

```toml
[project.entry-points."piloop.lineages"]
spine_only = "my_package:SpineOnly"
```

```text
[plugins.lineage]
use = "spine_only"
```

### The contract

A provider returns a `Graph`. The graph declares its own words: the kinds and the statuses of its nodes, each with a
label, and the tracks of its scores. A status also has a `Tone`, which colours it. piloop checks the graph when the
provider makes it: every name has an entry, every parent comes before its child, and the spine and the series are
paths of the graph. `[plugins.lineage] use` names the one instance of a campaign, `optimization` when it is unset.

<ContractLineage />

The built-in `optimization` has one node per candidate, with the candidate's parent:

| What | `optimization` |
|---|---|
| Kinds | The candidate's origin: `baseline`, `candidate`, `reference`, `recovered`, `skipped`. |
| Statuses | Where it stands in the pool of its track: `best`, `ranked` (it may be best), `scored`, `excluded`, `crashed`, `pending`, or `unscored` for an origin that piloop never scores. |
| Scores | The primary metric of each track, under the current evaluator. |
| Spine | The ancestry of the best of the first track, from the baseline. |
| Series | The new bests on the spine, each when it was scored best. |
| Links | The candidate, its idea, its run and the run's agent sessions. |
