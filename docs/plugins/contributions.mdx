A plugin can add tables, commands, skill parts, routes and consumers, as piloop's own plugins do. The built-in archive
provider, `local`, adds its tables, the `piloop restore` command and a consumer of the daemon's loop:

```toml
[project.entry-points."piloop.archives"]
local = "piloop.plugins.archive.local:LocalArchive"

[project.entry-points."piloop.schemas"]
"archive/local" = "piloop.plugins.archive.local.tables:SCHEMA"

[project.entry-points."piloop.commands"]
restore = "piloop.plugins.archive.local.cli:restore"
```

Its consumer comes from the `contribution()` of the archiver that it opens:

```python
class LocalArchiver:
    def contribution(self) -> Contribution:
        return Contribution(consumers=(Consumer(CONSUMER, WAKES, self._turn, Phase.UPKEEP),), lifecycle=self)
```

Two entries of one name in a group stop the daemon.

## Tables and migrations

A plugin keeps its tables in the home's database. It declares them in a `Schema`, with an entry point in
`piloop.schemas`. The entry point's name is the schema's: the provider that has the tables, such as `archive/local`, or
a name of the plugin's own. Every table that no plugin declares is core's.

```toml
[project.entry-points."piloop.schemas"]
lattice = "piloop_lattice.tables:SCHEMA"
```

```python
from pathlib import Path

from sqlalchemy import ForeignKey
from sqlalchemy.orm import Mapped, mapped_column

from piloop.capabilities import Base, Schema


class Rung(Base):
    __tablename__ = 'rungs'

    id: Mapped[int] = mapped_column(primary_key=True)
    campaign_id: Mapped[int] = mapped_column(ForeignKey('campaigns.id', ondelete='CASCADE'))


SCHEMA = Schema(tables=(Rung,), versions=Path(__file__).parent / 'migrations')
```

- `migrations/` is the plugin's own chain of Alembic revisions, `0001` first. piloop migrates core's chain first, then
  each plugin's, in one transaction. The `migrations` table has one row for core and for each plugin.
- A table references the plugin's own tables, or the `id` of a core table. piloop refuses any other reference, or a
  table that another schema has, before the daemon starts.
- `Schema.triggers` holds the triggers on the plugin's tables. Every connection creates the TEMP ones, and the
  plugin's revisions create the others.
- `Schema.protected` names the tables that `piloop sql` cannot write, and `Schema.hidden` the columns that it reads as
  NULL, such as a secret's value.
- When you uninstall the plugin, its tables, rows and revision stay, and piloop does not read them. When you install it
  again, it migrates from its own revision.

[CONTRIBUTING.md](https://github.com/hiloopai/piloop/blob/main/CONTRIBUTING.md#change-the-database-schema) shows how to
write a revision.

## Commands

An entry point in `piloop.commands` adds a command, or a group of them. Its name is the command's, and it names a
function or a cyclopts `App`:

```toml
[project.entry-points."piloop.commands"]
lattice = "piloop_lattice.cli:app"
```

`piloop` imports it only when the command runs, or when a help lists it. A name that piloop has is refused.

## Skills

An entry point in `piloop.skills` adds a part to one of piloop's skills, such as `piloop-operate`. Its name is the
part's, and it names a `SkillPart`:

```toml
[project.entry-points."piloop.skills"]
lattice-triage = "piloop_lattice.skills:TRIAGE"
```

```python
from importlib.resources import files

from piloop.cli.skills import SkillPart

TRIAGE = SkillPart('piloop-operate', 350, files(__package__) / 'triage.md')
```

- `piloop install-skills` writes each skill as its parts, by `order` and then by name, with a blank line between two.
  piloop's own parts of `piloop-operate` have the orders 100 (the loop), 200 (ideas and runs), 250 (pause and stop),
  300 (escalations), 400 (messages and decisions), 500 (candidates and the pool) and 700 (rules). So 350 goes right after
  the escalations.
- `replaces=('review',)` puts the part in place of piloop's part `review`. To replace a whole skill, replace each of its
  parts. The part that comes first starts with the skill's frontmatter.
- `piloop doctor` reports a skill that differs from what the installed packages compose.

## Routes and consumers

A provider that implements `contribution()` adds consumers while the daemon runs: jobs of the daemon's loop. A
consumer runs in the next turn after a new event of a kind that it wakes on, and when the time that it returned comes.
It reads the tables, not a queue of its own. Its `Phase` says when it runs in a turn: `CONFIGURE`, `UPKEEP`,
`IN_FLIGHT`, `OBSERVE` or `PLAN`, in that order. The daemon asks each provider that it opens, such as the archiver,
once. A consumer name that is taken already stops the daemon.

A provider that implements `routes(host)` adds a router: routes of the daemon's API, next to piloop's own. It returns
`Routes`, the router and what ends what the routes hold. A [network](/plugins/infrastructure#networks) says who may call
them. The selected provider of each capability of the home serves its routes, and so does each installed provider of a
capability that a campaign selects, built with its defaults. A route reads the database and its request only, because
every process that serves the API builds its own. When a route's method and path are taken already, the daemon does
not start.
