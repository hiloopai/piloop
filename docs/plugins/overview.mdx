A **plugin** is a Python package that you install next to piloop. This one adds a best rule, `min_gain`. It calls
the built-in rule `baseline` and changes one thing: a candidate whose gain over the baseline is below `min_gain` may
not be best.

```toml
[project.entry-points."piloop.best_rules"]
min_gain = "piloop_min_gain:MinGain"
```

```python
from piloop.capabilities import Baseline, Case


class MinGain(Baseline):
    min_gain: float

    def refuse(self, case: Case) -> str | None:
        if (why := super().refuse(case)) is not None:  # the built-in rule's reason
            return why
        return None if gain(case) >= self.min_gain else 'its gain is below min_gain'
```

`gain` is a short helper. The full rule is in [Best rules](/plugins/rules#best-rules). Install the plugin next
to piloop, check that piloop finds it, then select it in `piloop.toml` and run `piloop init .`:

```bash
uv tool install piloop --with ./examples/plugins/min-gain
piloop plugins
```

```text
[plugins.best_rule]
provider = "min_gain"
min_gain = 100
```

Each example plugin of these pages is a package in
[`examples/plugins/`](https://github.com/hiloopai/piloop/tree/main/examples/plugins). piloop's tests install each one
and select it.

## Core

piloop is a small **core** and a set of plugins. Core runs things: the SQLite database and its
[event feed](/reference/event-feed), the daemon's loop, the plugin host, the API and the CLI, and the leases that
hand jobs to workers. The plugins decide what to run, how to score it and where it runs. A plugin owns its tables and
migrations, and core owns every other table.

Ideas, runs, candidates, evaluations and the pool are the **campaign type** `optimization`, a plugin of piloop. Every
campaign is of this type. The [database schema](/reference/schema) lists each table under the plugin that owns it.

## Providers and capabilities

A **capability** is one kind of decision or service, such as the best rule. A **provider** is one implementation
of it, with a name. Each capability has at least one built-in provider, and your configuration selects one by its
name.

A provider is a class that subclasses its capability's contract. Its fields are its **parameters**, and its methods
are the contract. Import the contract, its types and the built-in providers from one module,
`piloop.capabilities`. The entry point's name is the provider's name.

A provider that needs something on the machine, such as a program on `PATH`, an extra or a login, returns it from
`checks()`, read only. `piloop doctor` runs it on every instance in use.

### What a package declares

| Slot | Entry point group | What it adds |
|---|---|---|
| Providers | the capability's group, for example `piloop.best_rules` | an implementation of a capability |
| Tables | `piloop.schemas` | its tables and its own chain of migrations |
| Commands | `piloop.commands` | a command or a group of commands of `piloop` |
| Skill parts | `piloop.skills` | a part of a skill, such as `piloop-operate` |
| A capability | `piloop.capabilities` | a capability of its own, that other plugins add providers to |

A provider that the daemon opens can also add consumers and routes. piloop declares its own providers, tables and
commands in the same groups, so a plugin can do anything that a built-in provider does.
[Tables, commands and routes](/plugins/contributions) shows each slot.

## Select a provider

A table selects a provider: `provider` is its name, and the other keys are its parameters.

- A capability with one provider per file has its own table, `[plugins.<capability>]`. The table is in `piloop.toml`
  for a campaign's choice, such as the best rule, and in `$PILOOP_HOME/config.toml` for the home's, such as the
  executor.
- A capability with several instances has a table for each, `[plugins.<capability>.<name>]`: `provider` is the one
  called `<name>` when the table has none. `[plugins.<capability>] use` names the instances in use, and a list of a
  role, such as its `sections` or `mcp`, names those that it uses.
- A provider that is a parameter of another, such as the `remote` of a CAS, is a table: `{ provider = "<name>", … }`.

piloop validates each table into the provider's class when it loads the file. An unknown name is an error that lists
the names that exist.

## Host and pure contracts

A **host** provider, such as a runtime, can get live objects of piloop: processes, files, a database session.

A **pure** provider gets data and returns data. The best rules and the stop rules are pure. A pure provider
imports only the standard library and, from `piloop.capabilities`, its contract and the built-in providers that it
calls. Its methods take and return data only:

- `str`, `int`, `float`, `bool`, `bytes`, an enum, a dataclass or a pydantic model of data, `list`, `tuple`, `dict`,
  and unions of these.
- No database session, file, function or other class.
- No `Any`, no `object`, no model that allows extra fields, and no type that contains itself.

A pure provider returns an error as a value, a case of a union. It does not raise. Data that costs database queries
is asked for by name first, as the stop rule's `reads` does.

## Call a built-in provider

A provider can subclass a built-in provider, call it with `super()`, and change one part of its answer, as `min_gain`
does above. The rest of the answer, and the built-in provider's parameters, stay the same.

## Let other plugins extend your plugin

A plugin can declare a capability of its own. Other plugins then add providers to it:

1. Make a `Capability` with its name and its contract, an abstract class. Its providers are entry points in the group
   `piloop.<name>s`.
2. Add an entry point in `piloop.capabilities` that names it.
3. Give your provider a field of the providers that it calls. `Annotated[P, CAP.entry]` takes a table
   `{ provider = "<name>", <its parameters> }`, and piloop refuses a name that no provider has when the file loads.

```python
class BestCheck(Parameters, ABC):
    @abstractmethod
    def check(self, case: Case) -> str | None: ...


BEST_CHECKS = Capability('best_check', BestCheck, tier=Tier.PURE)  # providers: piloop.best_checks


class Checked(Baseline):  # a best rule that calls the checks of its field `vetoes`
    vetoes: list[Annotated[BestCheck, BEST_CHECKS.entry]]

    def refuse(self, case: Case) -> str | None:
        held = [why for check in self.vetoes if (why := check.check(case)) is not None]
        return super().refuse(case) or ('; '.join(held) if held else None)
```

`piloop plugins` and `piloop doctor` list your capability and its providers.

## How piloop loads plugins

- **All or nothing.** piloop loads every provider of a capability and checks each one. Then it registers all of them,
  or none.
- **Before the daemon starts.** The daemon does not start when an entry point does not import, names an object of the
  wrong type, or has a name that another provider has. It also does not start when `config.toml` selects a provider
  that does not exist.
- **The same checks elsewhere.** `piloop serve --check`, `piloop doctor` and `piloop plugins` do the same checks.
  `piloop restart` and `piloop upgrade` do them first, and keep the daemon running if it would not start again.
